# Sudowork 项目记忆技术设计

> 状态：设计草案，尚未实现。
>
> 本文描述未来 Sudowork 支持“一个项目包含多个会话”时，项目记忆（Project Memory）的作用域、存储、读写、权限和 Scode 集成方案。
>
> 用户级 Memory 的历史背景与当前逻辑见：`docs/tech/Scode-Memory-历史背景与当前逻辑.md`。

## 1. 背景

里程碑 A 完成后，Sudowork 已将 Scode 用户级 Memory 与 Conversation Workspace 解耦：

```text
多个普通会话
→ 共享当前用户的 SUDOCODE_MEMORY_DIR
```

未来如果 Sudowork 增加项目功能，一个项目可能包含多个会话：

```text
项目 P
├── 会话 A
├── 会话 B
└── 会话 C
```

这些会话除了共享用户通用偏好，还需要共享项目背景、术语、约束和决策。例如：

```text
用户通用偏好：
- 使用中文回复
- 报价必须附来源

“华北报价”项目记忆：
- 客户主要关注交付时间
- 当前交付策略是先提供简版
- 该项目禁止使用数据源 B

会话 A 临时条件：
- 本次只查北京

会话 B 临时条件：
- 接着补查天津
```

用户级、项目级和会话级信息不能混成一套 Memory，否则会出现跨项目污染或临时条件永久化。

## 2. 设计目标

1. 同一项目下的多个会话可以共享项目事实、约束和决策；
2. 不同项目的 Memory 互相隔离；
3. 用户级 Memory 继续由 Scode 原生 `SUDOCODE_MEMORY_DIR` 管理；
4. 项目级 Memory 不复制到每个 Conversation Workspace；
5. Conversation Workspace 继续保持文件隔离；
6. 项目 Memory 写入必须经过项目身份和成员权限校验；
7. 支持结构化新增、更新、查询和删除；
8. 普通任务条件可以跨项目会话召回，但不能自动升级为永久项目规则；
9. 写入失败时，Scode 不得回复“已记住”；
10. 第一版不引入向量数据库、Markdown 双写或复杂管理 UI。

## 3. 非目标

第一版不处理：

- 多设备云同步；
- Remote/Moss 服务端项目 Memory；
- 全部历史会话全文自动注入；
- 项目知识库或文档管理；
- Skill 安装和启用；
- 复杂的 Memory 审批流；
- 由模型直接操作 SQLite 或任意项目文件。

## 4. 三层作用域

### 4.1 用户级 Memory

作用域：当前用户的所有普通会话和项目。

适合保存：

- 用户身份；
- 回复语言和格式偏好；
- 所有项目通用的业务规则；
- 用户明确要求长期保持的工作习惯。

当前实现：

```text
SUDOCODE_MEMORY_DIR=
~/.nexus/sudowork/sudocode/user-memory/<user-key>/
```

管理者：Sudowork 确定目录和用户隔离，Scode 管理 Memory 内容。

### 4.2 项目级 Memory

作用域：一个稳定 `project_id` 下的所有会话。

适合保存：

- 项目目标；
- 项目术语；
- 客户长期关注点；
- 已确认的技术或业务约束；
- 已作出的项目决策；
- 稳定的数据源、交付和协作规则；
- 项目成员职责。

管理者：Sudowork 主进程。

### 4.3 会话级 Context 与项目历史

作用域：当前 Conversation，或者同一项目内按相关性召回。

适合保存：

- 本次任务条件；
- 一次性附件说明；
- 某次执行结果；
- 当前进度、下一步和阻塞项；
- 尚未确认的讨论和候选方案。

原始事实来源：Sudowork 聊天数据库。

临时信息不等于不可跨会话。它可以在后续相关项目会话中被召回，但不能被当作永久项目默认值。

## 5. 推荐总体架构

```text
用户请求
  │
  ▼
Scode
  │
  ├── 原生 SUDOCODE_MEMORY_DIR
  │   └── 用户级 Memory
  │
  └── Sudowork Project Memory MCP
      │
      ▼
Sudowork 主进程
  ├── 根据 conversation_id 查询 project_id
  ├── 校验当前用户项目权限
  ├── 校验和过滤 Memory 内容
  ├── ProjectMemoryService
  └── SQLite project_memories
```

读取项目会话时：

```text
Scode 自动加载用户 Memory
+ Sudowork 读取当前项目 Memory
+ Sudowork 检索当前项目相关历史
+ 当前用户请求
```

写入项目 Memory 时：

```text
用户表达项目事实或决策
→ Scode 判断应写入项目 Memory
→ 调用 Sudowork Project Memory MCP
→ Sudowork 绑定当前项目并校验权限
→ 写入 SQLite
→ 读取验证
→ 返回结构化成功或失败结果
→ Scode 向用户报告结果
```

## 6. 为什么项目 Memory 由 Sudowork 管理

当前 Scode 的 `SUDOCODE_MEMORY_DIR` 适合一个用户级 Memory 根目录，但尚未确认支持同时挂载：

```text
User Memory + Project Memory
```

如果直接把 `SUDOCODE_MEMORY_DIR` 切换成项目目录，会丢失用户通用 Memory；如果复制用户 Memory 到每个项目目录，又会产生重复和冲突。

项目归属、成员权限、项目删除、协作和云同步也属于 Sudowork 产品域。因此推荐：

```text
用户 Memory
→ Scode 原生能力

项目 Memory
→ Sudowork 管理

项目历史召回
→ Sudowork 管理
```

如果未来 Scode 正式支持多个 Memory scope/root，可以重新评估是否将项目 Memory 下沉给 Scode 原生管理。

## 7. 谁决定写，谁真正写

推荐职责：

> Scode 理解语义并发起结构化项目 Memory 操作；Sudowork 主进程校验并真正持久化。

| 参与方 | 职责 |
|---|---|
| 用户 | 提供项目事实、规则、决策或删除指令 |
| Scode | 判断内容是否适合项目 Memory，并调用结构化工具 |
| Project Memory MCP | 将受限工具暴露给当前项目会话 |
| Sudowork 主进程 | 绑定项目、校验权限、过滤敏感信息、去重并持久化 |
| Renderer | 展示写入结果和来源，不直接操作内部存储 |

Scode 不应：

- 直接写 `PROJECT_MEMORY.md`；
- 直接访问 SQLite；
- 自己指定任意 `project_id`；
- 在主进程返回失败时宣称保存成功。

## 8. Project Memory MCP

### 8.1 是否需要 MCP

按当前 Scode 能力，推荐由 Sudowork 提供一个内置本地 MCP Server。

它不需要独立部署，可以随 Sudowork 打包并按项目会话注入。

注册规则：

```text
普通会话
→ 不注册 Project Memory MCP

项目会话
→ 注册 Project Memory MCP
→ MCP 绑定当前 conversation_id
```

### 8.2 最小工具集合

第一版只需要：

```text
project_memory_upsert
project_memory_list
project_memory_remove
```

`project_memory_clear` 涉及整个项目数据删除，可后置并要求用户二次确认。

### 8.3 `project_memory_upsert`

用途：新增或更新当前项目 Memory。

输入示例：

```json
{
  "category": "decision",
  "key": "delivery_strategy",
  "content": "客户关注交付时间，当前决定先提供简版",
  "sourceMessageIds": ["msg-123", "msg-456"]
}
```

输出示例：

```json
{
  "success": true,
  "memory": {
    "key": "delivery_strategy",
    "category": "decision",
    "content": "客户关注交付时间，当前决定先提供简版"
  }
}
```

### 8.4 `project_memory_list`

用途：查询当前项目 Memory。

输入示例：

```json
{
  "query": "交付策略"
}
```

输出应返回结构化 Memory 及来源，不直接暴露数据库或内部文件路径。

### 8.5 `project_memory_remove`

用途：删除当前项目的一条 Memory。

输入示例：

```json
{
  "key": "delivery_strategy"
}
```

删除前是否需要确认，由工具调用前的产品交互或主进程策略决定。

### 8.6 不允许模型传 `project_id`

工具输入中不应出现：

```json
{
  "projectId": "project-123"
}
```

Sudowork 应使用服务端可信链路：

```text
MCP 会话凭证
→ conversation_id
→ conversation.project_id
→ 当前用户项目权限
```

工具语义永远是“操作当前项目”，而不是“操作模型指定的某个项目”。

## 9. MCP 身份和权限

项目会话注册 MCP 时，应传入短期 capability token，而不是把以下信息直接暴露给模型：

- 数据库路径；
- 原始用户 Token；
- 可自由填写的 `project_id`；
- 其他项目的内部标识。

概念配置：

```json
{
  "name": "sudowork-project-memory",
  "command": "<bundled-node>",
  "args": ["<project-memory-mcp-entry>"],
  "env": [
    {
      "name": "SUDOWORK_CONVERSATION_TOKEN",
      "value": "<short-lived-capability-token>"
    }
  ]
}
```

主进程收到操作后必须验证：

1. token 有效且未过期；
2. token 绑定当前 `conversation_id`；
3. Conversation 存在且属于某个项目；
4. 当前用户仍有项目访问权限；
5. 操作类型符合当前成员权限；
6. 输入通过长度、类型和敏感信息校验。

MCP Server 不应直接拥有任意数据库访问能力，推荐调用受控服务层：

```text
MCP Tool
→ ProjectMemoryService
→ Database
```

## 10. 数据模型

推荐 SQLite 作为单一事实来源，Markdown 只作为可选导出格式。

示例表：

```sql
CREATE TABLE project_memories (
  id TEXT PRIMARY KEY,
  project_id TEXT NOT NULL,
  category TEXT NOT NULL,
  memory_key TEXT NOT NULL,
  content TEXT NOT NULL,
  source_conversation_id TEXT,
  source_message_ids TEXT,
  created_by_user_id TEXT,
  created_at INTEGER NOT NULL,
  updated_at INTEGER NOT NULL,
  UNIQUE(project_id, memory_key)
);
```

核心约束：

```text
UNIQUE(project_id, memory_key)
```

这样同一项目中相同语义键会更新，而不是无限追加冲突项。

例如：

```text
旧值：delivery_strategy = 先提供完整版
新值：delivery_strategy = 先提供简版
```

应执行 UPDATE，而不是保留两条同时生效的规则。

`source_message_ids` 第一版可以使用 JSON 字符串；如果后续需要精细来源管理，再拆关联表。

## 11. 写入流程

### 11.1 用户明确要求保存

用户：

```text
记住，这个项目的客户最关心交付时间。
```

Scode 调用：

```json
{
  "category": "stakeholder",
  "key": "customer_primary_concern",
  "content": "客户最关心交付时间",
  "sourceMessageIds": ["current-user-message-id"]
}
```

Sudowork 主进程：

```text
根据 conversation_id 查询 project_id
→ 校验当前用户权限
→ 校验输入
→ 按 project_id + key 查询已有记录
→ INSERT 或 UPDATE
→ 重新读取验证
→ 返回结构化结果
```

Scode 只有收到 `success: true` 后才能回复：

```text
已记住到当前项目：客户最关心交付时间。
```

### 11.2 用户修改项目 Memory

用户：

```text
把这个项目的交付策略改成先提供完整版。
```

Scode 调用相同 `key`：

```json
{
  "category": "decision",
  "key": "delivery_strategy",
  "content": "先提供完整版"
}
```

Sudowork 更新现有记录，不新增冲突项。

### 11.3 用户删除项目 Memory

用户：

```text
忘记这个项目关于数据源 B 的规则。
```

Scode 调用：

```json
{
  "key": "disabled_source_b"
}
```

Sudowork 验证并删除当前项目对应记录。

## 12. 普通聊天如何进入项目上下文

普通聊天默认进入项目会话历史，不应每句话都写入项目 Memory。

### 12.1 只进入项目历史

例如：

```text
这次只查北京。
今天先处理前三家。
这个附件是昨天导出的报价单。
```

这些是任务条件或一次性背景：

```text
保存到原始会话历史
→ 后续相关项目会话按需召回
→ 不写永久项目 Memory
```

### 12.2 可以进入项目 Memory

例如：

```text
这个项目统一使用人民币报价。
客户最终确认先提供简版。
该项目以后禁止使用数据源 B。
```

这些是稳定规则或明确决策，可以调用 `project_memory_upsert`。

### 12.3 自动提炼策略

第一版不额外启动一次模型总结任务。可以通过 Scode 系统规则要求：

- 明确项目规则和已确认决策时调用 `project_memory_upsert`；
- 临时条件只保留在会话历史；
- 不确定是否长期有效时不写永久 Memory；
- 用户明确说“记住到这个项目”时优先执行结构化写入。

后续如需自动提炼，可以在 Turn 或会话结束时生成候选项，但必须区分：

```text
decision / project_rule / stable_fact
→ 可进入项目 Memory

temporary_condition / execution_result / hypothesis
→ 只进入项目历史
```

## 13. 读取与注入

每次发送项目会话消息前，Sudowork 读取：

1. 当前项目稳定 Memory；
2. 当前项目相关历史；
3. 当前用户请求。

用户级 Memory 仍由 Scode 原生加载，不需要 Sudowork 重复注入。

示例：

```text
[Project Memory]
- 客户主要关注交付时间
- 当前交付策略：先提供简版
- 报价必须附来源

[Relevant Project History]
- 会话 A：已完成北京报价
- 会话 B：下一步需要补充天津

[User Request]
继续处理这个项目。
```

要求：

- 隐藏上下文不显示在用户消息正文；
- 标注来源会话和时间；
- 设置条数和字符上限；
- 当前会话已有内容不重复注入；
- 当前用户明确要求优先于历史内容；
- 当前文件和代码状态优先于历史摘要；
- 用户说“这次不要参考项目历史”时跳过本轮历史召回；
- 稳定 Project Memory 与相关历史必须分开标识。

## 14. Memory 作用域判断

在项目会话中，用户说“记住”时按以下规则分流：

```text
明确是个人通用偏好
→ User Memory

明确提到“这个项目”或内容明显只属于当前项目
→ Project Memory

当前任务的一次性条件
→ Project History

无法判断
→ 默认 Project Memory，或询问用户
```

默认项目级比默认用户级安全，因为不会污染其他项目。

保存成功后的回复应说明作用域：

```text
已记住到项目“华北报价”：客户主要关注交付时间。
```

或者：

```text
已记住为你的通用偏好：所有报价必须附来源。
```

## 15. 优先级

建议上下文优先级：

```text
系统与安全规则
> 当前用户明确要求
> 当前项目规则和决策
> 用户通用偏好
> 相关项目历史
> 模型默认行为
```

如果用户通用偏好是“输出详细报告”，但当前项目明确规定“只交简版”，则当前项目规则优先。

## 16. 为什么不直接写 Markdown

直接让 Scode 写：

```text
project-memory/<project-id>/PROJECT_MEMORY.md
```

虽然实现简单，但会带来：

- Agent 可能写错项目目录；
- 无法可靠校验成员权限；
- 多个会话并发写可能覆盖；
- 不容易结构化更新和去重；
- 删除单条 Memory 和删除项目难管理；
- Renderer 可能再次把内部文件当交付物；
- 未来协作和云同步迁移成本高。

因此推荐：

```text
SQLite = 单一事实来源
Markdown = 用户明确导出时生成的可选格式
```

## 17. 项目生命周期

### 17.1 项目改名

目录和数据按稳定 `project_id` 管理，改名不迁移 Memory。

### 17.2 删除会话

- 删除该会话原始历史；
- 删除或重建该会话对应的派生检索数据；
- 不自动删除项目稳定 Memory；
- 如果稳定 Memory 的来源只剩已删除消息，应标记来源缺失或重新确认。

### 17.3 删除项目

用户确认后删除：

- 项目 Memory；
- 项目历史索引；
- 项目与会话关联；
- 项目文件，按产品删除策略处理。

### 17.4 复制项目

创建新的 `project_id`。是否复制项目 Memory 应由用户选择，不能让新旧项目继续共享同一记录。

### 17.5 项目成员变更

成员退出或权限被移除后：

- 不能再调用项目 Memory MCP；
- 不能再读取项目 Memory；
- 已启动的 MCP capability token 应失效或在每次调用时重新校验权限。

## 18. 并发与一致性

多个项目会话可能同时更新同一 Memory。

第一版采用数据库事务和唯一约束：

```text
project_id + memory_key 唯一
```

更新时记录 `updated_at`。如后续出现高频协作冲突，再增加版本号或乐观锁：

```sql
version INTEGER NOT NULL DEFAULT 1
```

第一版不预先实现复杂冲突合并。

## 19. 敏感信息与边界校验

项目 Memory 写入前必须拒绝或清理：

- 密码；
- Token；
- API Key；
- 私钥；
- 验证码；
- 其他项目的数据；
- 无来源的模型推断；
- 超过长度限制的内容。

Memory 内容属于不可信数据。注入给模型时应明确标记为历史上下文，不能让其中内容覆盖系统安全规则。

## 20. 推荐实施阶段

### 阶段 A：项目与会话关系

- 增加稳定 `project_id`；
- Conversation 可选绑定 `project_id`；
- 完成项目成员和访问权限校验；
- 定义项目删除、改名和复制行为。

### 阶段 B：Project Memory 服务层

- 增加 `project_memories` 表和迁移；
- 实现 `ProjectMemoryService`；
- 实现 upsert、list、remove；
- 增加敏感信息和长度校验；
- 增加用户与项目权限测试。

### 阶段 C：内置 MCP

- 实现 Project Memory MCP Server；
- 为项目会话注入短期 capability token；
- 工具不接受 `project_id`；
- 将工具调用路由到 `ProjectMemoryService`；
- 验证写入失败不会返回成功。

### 阶段 D：读取和历史召回

- 每轮注入 Project Memory；
- 仅检索当前项目历史；
- 增加字符上限、去重和来源；
- 支持本轮忽略项目历史；
- 根据实际召回质量决定是否需要向量索引。

### 阶段 E：管理入口

按产品需要增加：

- 查看项目 Memory；
- 修改和删除；
- 清空确认；
- 查看来源会话；
- 导出 Markdown。

## 21. 最小可用版本

第一版只需要：

```text
project_id / conversation.project_id
+ project_memories 表
+ ProjectMemoryService
+ Project Memory MCP：upsert/list/remove
+ 每轮隐藏注入 Project Memory
+ 当前项目历史的最小文本检索
```

暂不实现：

- 向量数据库；
- Markdown 双写；
- 自动总结所有历史；
- 复杂管理页面；
- 多设备同步；
- 复杂冲突合并。

## 22. 验收场景

### 22.1 项目内跨会话

```text
项目 P / 会话 A：记住，这个项目的客户最关心交付时间。
项目 P / 会话 B：客户最关心什么？
```

预期：会话 B 回答“交付时间”。

### 22.2 项目隔离

```text
项目 P：禁止使用数据源 B。
项目 Q：允许使用数据源 B。
```

预期：两个项目规则互不污染。

### 22.3 用户 Memory 与项目 Memory 分离

```text
用户偏好：所有回复使用中文。
项目 P：交付物使用英文。
```

预期：普通交流使用中文，项目 P 交付物按项目规则使用英文。

### 22.4 临时条件不升级为永久规则

```text
项目 P / 会话 A：这次只查北京。
项目 P / 会话 B：继续上次北京的任务。
项目 P / 新任务：查询全部地区。
```

预期：会话 B 可以召回北京；新任务不会把北京当作永久默认地区。

### 22.5 修改同一 Memory

```text
项目 P：交付策略是先提供简版。
项目 P：把交付策略改成先提供完整版。
```

预期：更新同一 `delivery_strategy`，不同时保留两条冲突规则。

### 22.6 权限隔离

用户 A 被移出项目 P 后尝试通过旧会话调用 MCP。

预期：主进程拒绝读写，旧 capability token 不能绕过当前权限。

### 22.7 写入失败

模拟数据库写入失败。

预期：MCP 返回失败，Scode 不得回复“已记住”。

## 23. 一句话总结

```text
用户 Memory 属于用户，由 Scode 原生管理；
项目 Memory 属于稳定 project_id，由 Sudowork 通过受控 MCP 和 SQLite 管理；
临时任务信息属于项目历史，按相关性召回，不冒充永久项目规则。
```
