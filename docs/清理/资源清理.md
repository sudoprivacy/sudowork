### 3.3 移出构建期 TypeScript/Protobuf 工具

正式包中包含：

```text

@bufbuild/protoc-gen-es
@bufbuild/protoplugin
```

项目运行时需要的是 `@bufbuild/protobuf`，而 `@bufbuild/protoc-gen-es` 属于生成 Protobuf TypeScript 代码的构建期工具。目前它位于 `dependencies`，会被 electron-builder 当作生产依赖打入应用。

建议：

1. 将 `@bufbuild/protoc-gen-es` 移到 `devDependencies`。
2. 确认生产代码没有动态调用 TypeScript 编译器。
3. 重新打包并检查 `app.asar` 中是否还存在顶层 `typescript`。

预期收益：

| 指标       |    预计减少 |
| ---------- | ----------: |
| 安装后应用 | 约 30-60 MB |
| DMG/ZIP    |  约 5-10 MB |

优先级：**高**  
风险：**低到中**，需运行构建、类型检查和 Protobuf 相关测试。

## 4. 生产依赖图与打包过滤优化清单

### 4.1 修正生产依赖声明

#### 将 Protobuf 代码生成器移到开发依赖

`@bufbuild/protoc-gen-es` 只用于根据 `.proto` 生成 TypeScript 文件，运行时只需要 `@bufbuild/protobuf`。建议将其从 `dependencies` 移到 `devDependencies`：

```text
dependencies:
  @bufbuild/protobuf

devDependencies:
  @bufbuild/protoc-gen-es
```

生成结果已提交在：

```text
src/common/nexus/generated/
```

验收标准：

- `bun install` 后 lockfile 正常更新；
- `bunx tsc --noEmit` 通过；
- Protobuf 生成命令仍可运行；
- 最终 `app.asar/node_modules` 不再包含 `@bufbuild/protoc-gen-es`、`@bufbuild/protoplugin` 及其 TypeScript 依赖链。

#### 审计 Renderer-only 依赖

Renderer 依赖已经由 Vite 打入 `out/renderer`。纯 Renderer 依赖如果继续留在 `dependencies`，electron-builder 可能再次把原始 npm 包复制进 `app.asar/node_modules`。

可逐项审计：

```text
react
react-dom
react-router-dom
react-i18next
@arco-design/web-react
lucide-react
ahooks
swr
katex
```

确认某个依赖没有被 Main、Preload、Worker 或运行时动态导入后，可将其移到 `devDependencies`。不能批量移动：例如 `i18next` 当前被主进程直接引用，必须保留为生产依赖。

验收方法：以 `out/main/index.js` 和 `out/preload/*.js` 中保留的外部 `require()`/`import()` 为准，而不是只搜索 TypeScript 源码。

### 4.2 清理确定无用的包内文件

可在 `electron-builder.yml` 的 `files` 排除规则中处理：

```text
pptx2json/fixtures/**
better-sqlite3/deps/**
better-sqlite3/src/**
better-sqlite3/build/Release/obj/**
@larksuiteoapi/node-sdk/es/**
```

边界：

- `better-sqlite3` 必须保留 `lib/**`、`package.json` 和当前平台的 `better_sqlite3.node`；
- 飞书 SDK 主进程当前通过 CommonJS `require()` 加载，应保留 `lib/**`，只排除重复的 `es/**`；
- 不要使用宽泛的 `!**/dist/**`、`!**/build/**` 或 `!**/vendor/**`，这些名称经常包含运行时文件。

同时完善类型文件排除规则，覆盖：

```text
*.d.ts
*.d.mts
*.d.cts
*.d.ts.map
*.d.mts.map
*.d.cts.map
```

### 4.3 按目标平台裁剪原生文件

每个平台的安装包只保留当前系统和架构的二进制：

| 构建目标 | ONNX 保留目录 |
| --- | --- |
| macOS ARM64 | `darwin/arm64` |
| macOS x64 | `darwin/x64` |
| Windows x64 | `win32/x64` |
| Windows ARM64 | `win32/arm64` |
| Linux x64 | `linux/x64` |
| Linux ARM64 | `linux/arm64` |

重点裁剪：

```text
onnxruntime-node/bin/napi-v3/<非目标平台或架构>
node-pty/prebuilds/<非目标平台或架构>
其他原生依赖的非目标 prebuild
```

不要全局排除 `prebuilds/**` 或 `bin/**`。建议在 `afterPack` 中根据 `context.electronPlatformName` 和 `context.arch` 删除非目标目录，这比在 YAML 中维护多套互相覆盖的 glob 更不容易误删。

验收标准：

- 对每个发布平台分别构建；
- 检查目标 `.node`、`.dylib`、`.so` 或 `.dll` 仍存在；
- 应用可启动；
- 本地知识库可完成建库和检索；
- 终端可正常创建 PTY。

### 4.4 避免静态资源重复打包

当前 `public` 同时出现在：

```text
electron-builder.yml -> files -> public/**/*
electron-builder.yml -> extraResources -> from: public
```

这会让文件同时进入 `app.asar/public` 和 `Contents/Resources`。当前删除大图后 `public` 只剩很小的 `index.html`，但应明确选择一种归属，防止后续再次加入大资源时重复膨胀。

处理前需确认运行时代码从哪个位置读取 `public/index.html`。确认后删除另一条打包入口，不要同时保留。

### 4.5 高收益但需要专项验证的项目

#### `@xenova/transformers/dist/**`

Node 入口使用 `src/transformers.js`，`dist` 中包含浏览器 bundle 和多份 WASM。可尝试排除，但必须验证本地知识库完整流程。

#### `onnxruntime-web`

不能只通过打包过滤直接删除。Transformers 2.17.2 的 ONNX 后端静态导入 `onnxruntime-node` 和 `onnxruntime-web`，直接删包可能在模块加载阶段报错。可行路线是升级 Transformers，或维护一个只加载 Node 后端的最小补丁。

#### `@napi-rs/canvas`

它是 `officeparser -> pdfjs-dist` 的可选依赖。移除前必须回归 PDF/Office 文档解析，尤其是包含图片、字体和复杂布局的文件。

#### 重复 Sharp/Libvips

顶层 `sharp` 与 Transformers 内嵌的旧版 Sharp 使用不同版本，不能直接共用或删除其中一套。只有在升级依赖使版本收敛后，才适合做 dedupe。

#### `node-pty`

主进程当前直接使用 `@lydell/node-pty`，但打包配置还显式包含旧 `node-pty`。需要先确认旧包是否仍被其他生产依赖使用；确认没有调用后，再移除显式包含规则和对应依赖。

### 4.6 不应使用的清理方式

不要采用以下做法：

- 删除整个 `node_modules`；
- 根据目录名全局删除所有 `dist`、`build`、`vendor` 或 `prebuilds`；
- 只验证开发模式，不验证打包后的应用；
- 同时修改多类依赖后只比较一次体积；
- 为减小体积移除密钥存储、输入验证或必要的原生运行时。

## 5. 不建议优先处理的项目

### Electron Framework

Electron Framework 约 213 MB，是 Chromium、Node.js 和 Electron 原生运行时的主体。除非更换技术栈或升级到明显更小的 Electron 版本，否则清理空间有限。

### 内置 Node.js、Sudocode 和 Nexus

三项合计约 62 MB：

```text
Node.js   48 MB
Sudocode  8.8 MB
Nexus     5.4 MB
```

它们属于启动流程的核心运行时。移除后需要改为首次启动在线下载，会引入离线不可用、安装失败和首次启动时间增加等问题，不应作为第一批清理目标。

### `googleapis`

`googleapis` 解包后约 28 MB，但大部分是可高度压缩的 JavaScript 文本，压缩后约 1 MB。它影响安装后体积，但对 DMG 下载体积影响较小，清理优先级低于图片和原生二进制。

## 6. 推荐执行顺序

### 第一阶段：低风险直接收益

1. 删除未引用的 `public/big-paste-test.png`。
2. 将 `@bufbuild/protoc-gen-es` 移到 `devDependencies`。
3. 清理 `out/` 中旧版本 DMG、ZIP 和解包目录，避免本地磁盘误判。
4. 重新构建并记录 DMG、ZIP、`.app`、`app.asar` 的新体积。

预计 DMG 可从 373 MB 降至约 310-320 MB。

### 第二阶段：平台资源裁剪

1. macOS ARM64 包只保留 Darwin ARM64 的 ONNX 原生文件。
2. macOS x64、Windows、Linux 分别配置自己的排除规则。
3. 对每个平台执行安装启动、本地知识库建库和检索测试。

预计 DMG 可进一步下降约 18-20 MB。

### 第三阶段：可选原生依赖验证

1. 验证是否可以排除 `onnxruntime-web`。
2. 验证是否可以排除 `@napi-rs/canvas`。
3. 检查两套 Sharp/Libvips 是否可以合并或移除其中一套。

该阶段潜在收益较大，但测试成本和回归风险也最高。
