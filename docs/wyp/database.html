1总览：数据库做什么、不做什么

Sudowork 用 better-sqlite3（同步 API，避免 mutex 争用）作为唯一的结构化持久化存储，只在 主进程访问，渲染进程通过 IPC 桥间接查询。核心实现：

文件职责
src/process/database/index.tsSudoworkDatabase 类：所有 CRUD 方法（约 1400 行）
src/process/database/schema.ts全新安装时的基础建表 + 当前版本号 CURRENT_DB_VERSION = 22
src/process/database/migrations.tsv1→v22 的迁移脚本（演进表结构 / 约束 / 索引）
src/process/database/types.ts行类型 ↔ 业务类型（TChatConversation / TMessage）的转换
src/process/database/export.ts对外导出 getDatabase() 单例及备份/迁移工具
✅ 数据库承载
账户、会话、消息、定时任务、IM 渠道（插件/用户/会话/配对）、scode 自定义模型 provider
📄 文件承载（非 DB）
应用配置 / 偏好（sudowork-config.txt，Base64 JSON）：模型、MCP、主题、语言、各 Agent 鉴权 token
🗂 文件系统承载
图片、大文件附件、Agent 工作区文件；DB 只存路径引用（message.resultDisplay），不存图片元数据
⚙️ 关键配置：启动时执行 PRAGMA foreign_keys = ON（强制外键级联）与 PRAGMA journal_mode = WAL（读写并发）。数据库版本不靠表存储，而用 SQLite 内置的 PRAGMA user_version 跟踪。
⚠️ 文档纠偏：同目录的 database/README.md 已严重过时——它说当前版本 v4/v5、有 configs 表、有 gemini 会话类型。实际：版本已到 v22，没有 configs 表，会话类型只剩 acp / remote-agent（gemini/codex/nanobot 已在 v16 移除，openclaw-gateway 在 v21 迁移走）。本文以实际源码为准。

2存储边界：DB vs 文件 vs 文件系统

新人最容易搞混的就是"这个数据到底存哪"。记住这条分界：结构化、需查询/分页/外键的业务数据进 DB；全局应用配置走 .txt 文件；二进制大文件走文件系统、DB 只留路径。

数据位置实现
账户 / 会话 / 消息 / 定时任务 / 渠道 / 模型 providerSQLiteSudoworkDatabase
模型配置 model.config、MCP 配置 mcp.config、各 Agent 鉴权（acp.config 的 authToken/cliPath/yoloMode）、语言/主题/自定义 CSSconfig.txtConfigStorage（src/common/storage.ts），文件 sudowork-config.txt
会话历史的文件态备份txtsudowork-chat-history/<id>.txt（首启迁移 DB 的来源）
图片 / 附件 / 工作区产物文件系统{userData}/data/images/ 等，DB 内仅引用路径
纯 UI 临时态（侧栏折叠等）localStorage渲染进程，不持久化到后端
💡 为什么 API Key / 鉴权 token 不在 DB？大模型 provider 的 key、各 ACP 后端的 authToken 都存在 config.txt 里（IConfigStorageRefer）。DB 里唯一的密钥相关表是 scode_custom_model_providers（scode 专用自定义 provider 的 base_url/api_key）。排查"模型配置丢了"要去看文件，不是 DB。

3数据库承载的功能（按业务域）

① 账户系统
WebUI 登录、密码、JWT 密钥
② 对话核心
会话 + 消息持久化、分页、流式落库
③ 定时任务
cron_jobs：调度 + 运行状态
④ IM 渠道
插件 / 授权用户 / 会话 / 配对码
⑤ scode 模型
自定义 provider 存储
⑥ 版本管理
user_version + 迁移历史

① 账户系统 users

支撑 WebUI / 远程访问的登录鉴权。存用户名、bcrypt 密码哈希、每用户的 jwt_secret（用于签发/校验会话 token）、头像路径、最后登录时间。提供 getSystemUser()、hasUsers()、updateUserPassword()、updateUserJwtSecret() 等。--resetpass 即更新此表的密码哈希并轮换 jwt_secret 使旧 token 失效。

⚠️ 最易混淆点：本地 users 表 ≠ 产品登录账号。产品意义上的"登录注册"（个人手机号 / 企业账号）走的是后端接口（中控 / MOSS），那套身份存在 localStorage（sudowork_auth_v2 / eeclaw_auth_v1）+ config.txt，不会写入本地 users 表。本地 users 表只有两个作用，且通常落在同一行上：
作用说明
① WebUI 门禁账号浏览器访问 WebUI 时的那道本地登录（默认 admin + 随机密码，--resetpass 重置）。用 bcrypt 校验、用该行 jwt_secret 签 sudowork-session cookie。纯本地，与中控/MOSS 无关；桌面 GUI 模式不会用到
② 本地数据 ownerconversations.user_id 外键指向它。桌面/单用户场景所有会话都归属占位行 system_default_user（defaultUserId）；不传 userId 时默认用它

初始化时若只有 system_default_user 占位行，会直接把它的用户名/密码设成 admin —— 所以本地实际就是一个账号，既当 WebUI 登录、又当所有本地数据的 owner。两套身份互不写入：手机号登录不在本地 users 建行，本地 admin 也不同步到后端。详见 远端接口清单。

② 对话核心 conversations + messages

整个产品最核心的持久化。conversations 存会话元数据：类型（acp 本地 / remote-agent 企业远程）、名称、工作区等 extra(JSON)、model(JSON)、状态、来源 source（aionui / telegram / lark / dingtalk / wechat...）、渠道会话隔离 channel_chat_id。messages 存每条消息：type(text/tool_call/plan/acp_permission...)、content(JSON)、position(left/right/center/pop)、status(finish/pending/error/work)。

关键方法：createConversation / getUserConversations(分页) / insertMessage(s) / getConversationMessages(分页+排序) / findChannelConversation（按来源+chatId 复用渠道会话）。删除会话时外键级联自动清空其消息。

③ 定时任务 cron_jobs

支撑 24/7 自动化（CronStore 在 src/process/services/cron/CronStore.ts 读写此表）。存调度方式（at/every/cron + 值 + 时区 + 人类可读描述）、要发送的 payload_message、归属会话、Agent 类型、创建者（user/agent）、以及运行时状态（next_run_at / last_run_at / last_status / run_count / retry_count）。后续迁移还加了 conversation_mode(复用/新建会话)、workspace、preset_assistant_id。

④ IM 渠道（Channels）assistant_plugins / assistant_users / assistant_sessions / assistant_pairing_codes

📌 命名陷阱：这 4 张表表名是历史遗留的 assistant_*，但代码里全部通过 getChannelPlugins() / getChannelUsers() / createPairingRequest() 这类 Channel* 方法访问。看到 assistant 表 = 就是 IM 渠道数据。
  • assistant_plugins：各 IM 平台机器人配置（type、enabled、加密后的 config 凭证、运行状态机 status、最后连接时间）。
  • assistant_users：授权白名单——哪些平台用户被允许使用（platform_user_id + platform_type 唯一）。
  • assistant_sessions：平台用户 ↔ 内部会话(conversation_id) 的映射 + 工作区 + chat_id。
  • assistant_pairing_codes：配对授权流程的 6 位码（状态 pending/approved/rejected/expired + 过期时间），cleanupExpiredPairingRequests() 定期清理。

⑤ scode 自定义模型 provider scode_custom_model_providers

按 (user_id, provider_id) 主键存 scode 的自定义模型接入：base_url / api_key / models(JSON)。方法 getScodeCustomModelProviders / replaceScodeCustomModelProviders。

⑥ 版本管理

无独立表。当前结构版本写在 PRAGMA user_version，迁移历史由 getMigrationHistory() 提供。vacuum() 回收空间。

5版本与迁移系统

启动时对比 PRAGMA user_version 与 CURRENT_DB_VERSION(=22)，在单个事务内顺序执行缺失的迁移（任一失败则整体回滚）；全部用 IF NOT EXISTS 保证幂等。由于 SQLite 不支持 ALTER 修改 CHECK 约束，凡是改会话/插件类型枚举的迁移都用"建新表 → 拷数据 → 删旧表 → 改名"的套路（migrations.ts 里大量 conversations_new 即此）。

版本内容
v1初始 Schema（users / conversations / messages）
v2性能复合索引
v3 / v5全文搜索（跳过）/ 清理 FTS 表
v4移除 user_preferences 表
v6users 加 jwt_secret
v7新增 4 张 Personal Assistant（渠道）表
v8conversations 加 source
v9新增 cron_jobs 表
v10 / v12 / v14 / v15逐步放开渠道类型/来源约束（lark、dingtalk、扩展渠道）
v11 / v13会话类型曾加入 openclaw-gateway / nanobot
v16移除 gemini / codex / nanobot 会话类型
v17 / v18 / v19cron_jobs 加 conversation_mode+last_conversation_id / workspace / preset_assistant_id
v20会话类型加入 remote-agent（企业远程）
v21把历史 openclaw-gateway 会话迁移为 acp/scode
v22新增 scode_custom_model_providers 表
🔄 首启迁移：历史文件存储（sudowork-chat-history/*.txt）会在首次启动时自动迁移进 DB，无需手动操作（migrateFileStorageToDatabase()）。

7注意点 / 易踩坑

  • README 过时：database/README.md 停在 v4/v5，且提及的 configs 表、gemini 类型均不存在。以 schema.ts + migrations.ts 为准。
  • 表名 ≠ 业务名：assistant_* 四表实际是 IM「渠道」数据，通过 getChannel* 方法访问。
  • 密钥分散两处：大模型/ACP 鉴权 token 在 config.txt（非 DB）；只有 scode 自定义 provider 的 key 在 DB 的 scode_custom_model_providers。
  • 改 CHECK 约束需走"建新表迁移"，不能直接 ALTER；新增枚举值记得同步 schema.ts 基础建表 + 写一条迁移。
  • 外键级联已开启：删用户级联删其会话，删会话级联删其消息（删渠道用户级联删其会话映射）。
  • 图片不入库：仅在 message.content/resultDisplay 存文件系统路径。
  • 加新表/字段流程：① schema.ts 建表（新装）② migrations.ts 写迁移（老库升级）③ 抬高 CURRENT_DB_VERSION ④ index.ts 加 CRUD ⑤ types.ts 加行类型。
