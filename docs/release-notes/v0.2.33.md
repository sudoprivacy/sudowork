# Sudowork v0.2.33 Release Notes

Since v0.2.30: 45 commits excluding merges. This release includes the shared
browser work prepared for v0.2.31 and the subsequent Desktop, packaging and
viewer fixes. The v0.2.32 publication was cancelled after a packaged browser
adapter defect was found; v0.2.33 contains its repair.

## Shared browser sessions

- Desktop and WebUI share the React browser panel, navigation, session files,
  lifecycle controls and authenticated viewer. AI and users operate the same
  browser, persistent profile and selected tab.
- Desktop owns an isolated native Chrome session for each local conversation.
  Standalone CDP is the default; managed extension mode is an explicit option.
  Cloud sessions use isolated owner profiles and support managed extension
  and CDP transports. The model selects headless or headful browsing according
  to the task and available capabilities.
- Take control waits for the runtime to acknowledge a pause of main and child
  agent tool execution. Return to AI carries a note and a fresh observation.
  Disconnecting the viewer preserves human control until explicit recovery.
- Desktop has compact controls that stay above native Chrome. The main panel,
  compact controls and independent viewer share the same session and lease.
- Page and native window views attach on demand. Starting automation does not
  allocate a viewer; stopping headful Chrome releases its display resources.
- Native chooser uploads and verified downloads use authenticated session
  routes. Ordered human input completes before Return to AI; stale targets,
  old choosers and anonymous file requests are rejected.
- The published browser dependency is ai-dev-browser v0.57.5. Desktop bundles
  scode v0.2.31, including acknowledged runtime pause and browser MCP support.

## Reliability and installation

- Browser status readers no longer interrupt one another or discard a human
  control capability during ordinary polling.
- Bounded tab and download lists leave space for the browser image when a
  persistent profile has accumulated history. Firefox is covered by the
  committed live file journey alongside Chromium.
- Reloading while a one-time tool approval is pending retains the approval
  and completed conversation history.
- The post-release live journey waits for the refreshed document and visible
  conversation controls, rather than requiring every resource to finish loading.
- Both browser MCP entry points are compiled for clean installations and
  included in Desktop resources. Packaging rejects missing or empty entries
  before signing. Platform builds select their target architecture explicitly.
- WebUI offline packages include native AMD64 or ARM64 application and
  PostgreSQL images, with checksum verification and a shared installer.
- ACP test cleanup waits for actual daemon runtime retirement before calling
  protected shutdown. The service's active-runtime guard remains in force.

## Other changes since v0.2.30

- Installed agent cards open the latest conversation or create one using a
  stable template identity.
- Personal and managed cloud conversations preserve the owner's selected
  model, organization and authorized history.
- Agent and account changes load matching history and reset cached drafts.
  Reloaded idle sessions and cancelled model selection show current state.
- Artifact history survives browser handoff and conversation reload; the
  shared cancel control has an accessible name.

## Validation and production delivery

- Final implementation PR #1254 passed all 36 applicable checks, with one
  conditional skip. The root suite passed 3,179 tests with 28 existing skips.
- Actual packaged Windows browser adapters passed headless and headful Chrome
  journeys. The published v0.2.33 Windows ZIP was subsequently downloaded,
  checked against GitHub's SHA-256 asset digest, and passed both journeys using
  its own packaged executable and browser adapter. A clean build produced both
  required transport entry points.
- Published scode v0.2.31 passed three real API ACP cases on Windows and three
  in Linux with an init process, including cancellation and session recovery.
  Twenty consecutive Linux protocol runs passed all 40 cases.
- Real Desktop model acceptance covered native Chrome, compact controls,
  acknowledged handoff, trusted Unicode input and exact AI readback.
- The public WebUI was upgraded at `webui.sudoprivacy.com` to the tested source
  tree of v0.2.33. The original authenticated browser retained its identity,
  cookie and old script assets. PostgreSQL, TLS, encryption keys and existing
  conversation execution states were preserved.
- Production Moss v0.1.59 uses runtime SDK v0.1.2 and browser SDK v0.57.5.
  Restricted Secret patch acceptance and persistent profile preservation
  passed without changing runtime RBAC.
- Public Firefox and Chromium acceptance passed against that deployment with a real model,
  independent viewer return, pending approval recovery, trusted Unicode
  replacement, native upload and exact downloaded bytes. Sixteen retained
  downloads remained accessible in Firefox; Chromium retained 18. Desktop Chromium and Firefox journeys also
  passed against the production backend before the frontend upgrade.
- The initial public Chromium run timed out while waiting for a reload's full
  load event. Failure evidence was retained. Five consecutive pending-session
  reloads recovered visible conversation controls, and the full real model
  journey passed with document readiness plus the existing UI assertions.
- Public lifecycle acceptance passed headful extension startup, headless
  restart, explicit headful CDP, persistent cookies, display release and a real
  AI continuation while Chrome stayed stopped. Its live test now makes the
  stopped-profile prerequisite explicit, selects its initial transport, and
  shares visible one-time permission handling with the file journey.
- The external-human handoff mode passed a real-model preflight with a separate
  touch-enabled Chromium viewer at 390 by 844. It required trusted Unicode
  input, exactly one submission, unchanged browser/profile identity and exact
  AI readback after Return. This preflight does not count as a physical phone
  or Safari result.

The production browser deployment remains a controlled owner pilot. Global
resource admission and idle eviction, pairing an existing personal Chrome
profile, and a cloud-to-local extension relay are follow-up work. Physical
iPhone/Safari acceptance requires an actual device and is tracked separately.
