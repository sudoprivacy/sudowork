一、对提案的三点核对（请 owner 关注）

① §6.3「回车 queue / 上键 dequeue 已在 sudocode CLI 验证」— 与代码不符 更正

sudocode 交互式 REPL 是同步 readline + Ctrl-C（main.rs:1441-1517、input.rs），没有消息队列、没有 Up-dequeue 绑定。message queue 属纯新建功能，不能按“对齐 sudocode 现有行为”来估工。

② §8.1#6「等当前工具执行完毕后中断」— 过于悲观 更正

sudocode 用 kill_on_drop 协作式杀掉正在执行的前台命令（bash.rs:214-248，单测 abort_signal_interrupts_foreground_command），不是等它跑完。§8.2 的「≤500ms」因此更可达。建议 #6 改为“中断会终止正在执行的命令”。

③「不需要回滚 / LLM 自行处理一半的工作」— 应升级为“已验证的硬保证” 利好

sudocode 在全部 4 条中断路径上，为每个悬空 tool_use 合成 error tool_result 并追加 [interrupted]（conversation.rs:478-566，测试 :2487）。因此下一次请求不会因未配对 tool_use 被 Anthropic 拒绝。这是硬保证，不是靠 LLM 自觉——本功能最大的正确性风险已消除。

三、架构

3.1 运行时隔离 — 两个队列不会同时存在于同一实例

sudocode 进程要么是「交互 REPL」（人在用 CLI，用它自己的队列），要么是「ACP server」（被 sudowork 驱动，用 sudowork 的队列）——互斥的运行模式，无运行时竞争。需要一致的是行为语义，让用户在两个产品间切换体验一致。

flowchart LR
  H["👤 人在 CLI"] --> REPL["sudocode：交互 REPL 模式
(它自己的队列)"]
  SW["sudowork"] --> ACPM["sudocode：ACP server 模式
(sudowork 的队列)"]
  REPL -. 互斥 · 不同时 .- ACPM

为什么"互斥"是硬保证，而不是靠自觉 by design · 已核验

这不是运行时判断，是构造上的分离——scode 启动时按 argv 二选一，分派到两个互不引用的顶层函数：scode acp → run_acp_server（作为 sudowork 的引擎），scode → run_repl → run_repl_async_dispatch（交互队列）。同进程内不可能两者并存。

  • 队列模块只接在 REPL 分支：input_queue / repl_async 仅被 run_repl 一侧引用；ACP 路径对它零引用（grep 核验 0 命中）——一次误改无法把队列泄漏进引擎路径。
  • 旋钮漏不进 ACP：SUDOCODE_INTERRUPT_QUEUE_MODE（默认 off → 同步 REPL 字节一致）只在 run_repl 读取；ACP 模式完全无视它。
  • 引擎连开关都看不到：sudowork spawn scode 时从不设这个 env（grep 核验空）——作为引擎的 scode 侧根本拿不到这个旋钮。

所以「两个队列不会同时存在于同一实例」是编译期 / 结构性保证，强于任何运行时守卫——不需要额外断言测试来兜底。interrupt 侧同理：ACP 模式走 session/cancel 处理器、REPL 模式走 HookAbortSignal，两条入口各自独立，最终都汇入 scode 既有的轮中止（见 §二）。

3.2 共享行为规范（两个产品都实现同一套）

flowchart TD
  M["回复进行中：来了新消息 / 回车"] --> Q1{"autoInterrupt?"}
  Q1 -->|"ON"| I["session/cancel 当前轮
→ 立即发送新消息"]
  Q1 -->|"OFF"| Q2{"messageQueue?"}
  Q2 -->|"ON"| E["入队；轮结束（自然/stop）时全部合并为 1 条 user message 发出（1 次 API call）"]
  Q2 -->|"OFF"| B["维持现状：回复中不可提交"]
队列 OFF队列 ON
auto-interrupt OFF回复中不可提交（当前行为）全部暂存，轮结束（自然完成 / 用户 stop）时合并为 1 条 user message 一次发出
auto-interrupt ON发送即打断第一条立即打断并单独作为新轮启动；启动后再来的走队列 ON 语义（同左格：结束时合并 1 次发出）

上键（输入框空、队列非空）→ dequeue 最后一条回编辑框。打断 = 真正的轮中止，留下事务完整的 [interrupted] 轮（由 sudocode 保证，见 §二）。
合并语义：flush 时把 N 条排队消息按提交顺序拼成 1 个 user message（每条前加 "> " 前缀分隔或简单换行拼接由实现选定），下游 session/prompt 只发 1 次——tokens 更省，也贴合"我攒着一起说完"的用户心理模型；不是 N 次独立 turn 的串行回放。

3.3 sudowork：单一进程侧协调器（SSOT + DRY）

把「用户输入 vs 轮边界」的决策收敛到一个进程侧模块，桌面 IPC 与微信渠道都走它。理由：轮状态 SSOT 本就在进程侧任务（AcpAgent）；纯前端队列无法服务微信（无 renderer），会变成两套实现两个 SSOT。今天该决策散在两处（renderer 禁提交；ChannelMessageService.ts:243 直接丢弃第二条微信消息并提示“请稍候”）——统一到协调器是系统性修复，而非逐处打补丁。

3.4 键盘/输入处理（为什么要 guard）

新增的按键行为要和 sendbox 现有的键盘逻辑共存——技能选择弹窗、斜杠命令弹窗、以及多行文本的光标移动都用同一套 onKeyDown。所以每个新键都带触发条件（guard），只在无歧义时生效，绝不抢占既有按键：

flowchart TD
  K["按键 · sendbox onKeyDown"] --> W{"技能/斜杠 弹窗打开?"}
  W -->|"是"| POP["交给弹窗
上下选择 / 回车确认"]
  W -->|"否"| KEY{"哪个键"}
  KEY -->|"Enter"| R1{"回复进行中 且
两个开关都关?"}
  R1 -->|"是"| WARN["提示‘回复进行中’
维持现状 · 不提交"]
  R1 -->|"否"| SUBMIT["提交 → 协调器
发送 / 入队 / 打断"]
  KEY -->|"Esc"| E1{"回复进行中?"}
  E1 -->|"是"| INT["打断当前轮 · stop"]
  E1 -->|"否"| DEF1["默认 · 无操作"]
  KEY -->|"↑ Up"| U1{"输入框为空 且 队列非空?"}
  U1 -->|"是"| DEQ["dequeue 最后一条 → 回填输入框"]
  U1 -->|"否"| DEF2["默认 · 光标/历史移动"]

Guard 的意义：① 弹窗打开时按键归弹窗；② 两开关都关时 Enter 维持“回复中不可提交”（避免产生 no-op 丢消息）；③ Esc 仅在回复进行中才打断；④ ↑ 仅在输入框为空且队列非空时才 dequeue，否则照常移动光标——避免误伤多行编辑。
