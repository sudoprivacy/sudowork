# Renderer UI Token 硬切迁移方案

日期：2026-07-31  
状态：方案已确认，待实施

## 1. 背景

当前 Renderer 同时存在多套颜色和主题表达：

- `src/renderer/styles/variables.css` 中的项目语义 Token；
- `--bg-1`、`--color-bg-1`、`--color-text-1` 等历史兼容 Token；
- Arco Design 的 `--color-*`、`--arcoblue-*` 等第三方 Token；
- `uno.config.ts` 暴露的旧颜色 utility 和 shortcut；
- 页面 CSS、TSX inline style、UnoCSS class 中的硬编码颜色；
- Markdown Shadow DOM、xterm、CodeMirror、ECharts、Diff/Code Viewer 等独立主题入口；
- `[data-theme='dark']`、`body[arco-theme='dark']` 和少量无效 `dark:` utility 并存。

继续增加兼容别名会隐藏旧代码，让页面看似正常但无法判断是否已完成迁移。项目接下来还会进行大量功能 Review 和代码精简，因此本次采用硬切策略：直接删除旧项目 Token，仅保留新规范 Token；视觉问题随后按功能区域逐个暴露、审查和修复。

CSS 自定义属性缺失通常不会造成 React 或 TypeScript 运行时异常，而是使对应 CSS 声明失效、发生继承或退回浏览器默认样式。因此“页面崩坏”主要指视觉回退、边界消失、颜色错误和明暗模式不一致，不代表允许功能逻辑、数据安全或可访问性基础能力失效。

## 2. 已确认决策

1. 新设计 Token 是唯一项目规范，不建立旧 Token 兼容层。
2. 删除旧项目颜色 Token 定义及其 UnoCSS 映射，不新增 `legacy-tokens.css`。
3. 不对旧 Token 做全局机械替换；页面 Review 时按实际语义重新选择新 Token。
4. Arco Design 自身 Token 作为第三方桥接保留，但只允许在 Arco 桥接文件中定义和使用。
5. Arco 主要操作色使用中性 Primary：
   - 亮色：`#0D0D0D`
   - 暗色：`#E5E5E5`
6. 品牌色独立使用 `#C96442`，不继续承担全局 Primary 的职责。
7. 保持项目当前系统字体栈，不引入 `GoogleSansFlex` 或新字体资源。
8. 第一阶段只完成 Token 与主题基础设施硬切，不顺手逐页修复所有视觉问题。
9. Token 分类和桥接注释统一使用中文。

## 3. 目标与非目标

### 3.1 目标

- 建立唯一、清晰的新项目 Token 集合。
- 删除旧项目 Token 和旧 UnoCSS 颜色接口，让存量依赖显式暴露。
- 建立新 Token 到 Arco 的单向桥接。
- 统一项目明暗模式入口，消除首屏强制亮色和无效 `.dark` 依赖。
- 为后续按功能区域 Review、样式修复和代码精简提供可搜索的债务清单。
- 保证新增业务代码只能使用新 Token 或明确的组件局部变量。

### 3.2 非目标

第一阶段不负责：

- 修复全部页面的视觉回归；
- 重写登录页、Setup 页、Workspace 或 Task Panel；
- 统一 Markdown、终端、编辑器、图表等隔离渲染器的全部配色；
- 删除所有硬编码颜色；
- 调整字号、间距、圆角和阴影的产品设计；
- 引入字体文件或更换现有字体；
- 为旧主题或扩展主题提供向后兼容。

## 4. 设计原则

### 4.1 单一真值来源

项目规范 Token 只在以下文件定义：

```text
src/renderer/styles/variables.css
```

亮色值定义在 `:root`，暗色值定义在 `[data-theme='dark']`。

### 4.2 不保留兼容别名

禁止以下做法：

```css
/* 禁止：这会继续掩盖旧消费者 */
--bg-1: var(--secondary);
--text-secondary: var(--foreground-secondary);
--danger: var(--destructive);
```

旧 Token 被删除后，消费者必须在对应页面 Review 时迁移。

### 4.3 按语义迁移，不按旧值迁移

同一个旧 Token 在不同页面可能承担不同职责。例如 `--bg-1` 可能表示应用背景、卡片背景、侧栏背景或控件背景，不能统一替换为某一个新 Token。

迁移时优先回答“这个元素是什么”，再选择：

- 页面底色：`--background`
- 卡片：`--card`
- 浮层：`--popover`
- 次级区域：`--secondary`
- 弱背景：`--muted`
- 强调/交互区域：`--accent`
- 控件填充：`--fill-*`

### 4.4 第三方桥接不成为业务接口

Arco 的 `--color-bg-*`、`--color-text-*`、`--color-fill-*`、`--color-border-*` 等变量属于第三方实现细节。

- 可以在 `arco-override.scss` 中由新 Token 派生；
- 业务 CSS、TSX 和 UnoCSS class 禁止直接引用；
- 现有业务引用在后续页面 Review 中逐步移除；
- 不因为名称旧而直接删除 Arco 内部所需变量，否则第三方组件会失去主题桥接。

### 4.5 新代码不增加页面级硬编码主题色

以下情况除外：

- 文件格式、语法高亮或协议规定的固定颜色；
- 品牌资源自身颜色；
- 第三方库必须接收的计算后颜色，但其来源仍应是新 Token；
- 临时调试代码，且不得进入提交。

## 5. 新规范 Token

项目使用完整 CSS 颜色值，例如 `rgb(13 13 13)`，不使用仅包含 `R, G, B` 通道的值。原因是当前代码大量直接使用 `color: var(--foreground)`，完整颜色值可以直接消费。

需要透明度时优先使用：

```css
color-mix(in srgb, var(--brand) 12%, transparent)
```

而不是继续增加 `--*-rgb` 通道型兼容 Token。

### 5.1 背景

| Token | 亮色 | 暗色 | 语义 |
|---|---|---|---|
| `--background` | `rgb(255 255 255)` | `rgb(10 10 10)` | 应用和页面基础背景 |
| `--card` | `rgb(255 255 255)` | `rgb(23 23 23)` | 卡片和独立内容容器 |
| `--popover` | `rgb(255 255 255)` | `rgb(23 23 23)` | 弹出层、菜单和浮层 |
| `--secondary` | `rgb(245 245 245)` | `rgb(38 38 38)` | 次级区域背景 |
| `--muted` | `rgb(248 248 248)` | `rgb(23 23 23)` | 弱化背景 |
| `--accent` | `rgb(240 240 240)` | `rgb(51 51 51)` | 悬停、选中和强调背景 |

### 5.2 前景文字

| Token | 亮色 | 暗色 | 语义 |
|---|---|---|---|
| `--foreground` | `rgb(13 13 13)` | `rgb(250 250 250)` | 主要文字和图标 |
| `--foreground-secondary` | `rgb(77 77 77)` | `rgb(212 212 212)` | 次要文字 |
| `--foreground-tertiary` | `rgb(130 130 130)` | `rgb(82 82 82)` | 提示和弱化文字 |
| `--foreground-quaternary` | `rgb(163 163 163)` | `rgb(64 64 64)` | 禁用和最低强调文字 |

反色文字保留为项目扩展：

```text
--foreground-white
--foreground-white-secondary
--foreground-white-tertiary
--foreground-white-quaternary
```

### 5.3 Primary 与品牌色

| Token | 亮色 | 暗色 | 语义 |
|---|---|---|---|
| `--primary` | `rgb(13 13 13)` | `rgb(229 229 229)` | 主要操作和高强调控件 |
| `--primary-foreground` | `rgb(255 255 255)` | `rgb(13 13 13)` | Primary 上的内容 |
| `--brand` | `rgb(201 100 66)` | `rgb(201 100 66)` | 品牌强调 |
| `--brand-foreground` | `rgb(255 255 255)` | `rgb(255 255 255)` | Brand 上的内容 |
| `--secondary-brand` | `rgb(250 240 236)` | 第一阶段沿用亮色值并实测 | 品牌弱背景 |
| `--secondary-brand-foreground` | `rgb(13 13 13)` | `rgb(255 255 255)` | 品牌弱背景上的内容 |

`--secondary-brand` 的暗色值在来源主题中未提供独立值。第一阶段保留同值以忠实迁移；后续页面 Review 时若对比度不足，再以可访问性检查结果确定暗色值，不能凭感觉新增色值。

### 5.4 功能色

| Token | 亮色 | 暗色 |
|---|---|---|
| `--destructive` | `rgb(220 38 38)` | `rgb(248 113 113)` |
| `--link` | `rgb(37 99 235)` | `rgb(96 165 250)` |
| `--warning` | `rgb(217 119 6)` | `rgb(251 191 36)` |
| `--success` | `rgb(22 163 74)` | `rgb(74 222 128)` |
| `--blue` | `rgb(44 85 251)` | `rgb(91 116 251)` |
| `--orange` | `rgb(234 88 12)` | `rgb(242 120 50)` |
| `--violet` | `rgb(124 58 237)` | `rgb(168 120 245)` |

每个功能色对应一个前景 Token：

```text
--destructive-foreground
--link-foreground
--warning-foreground
--success-foreground
--blue-foreground
--orange-foreground
--violet-foreground
```

来源主题没有 `info`，因此删除旧 `--info`。原有信息提示必须在页面 Review 时根据语义选择 `--link`、`--blue` 或其他新 Token，不能保留含糊别名。

### 5.5 边框、填充与覆盖层

| Token | 亮色 | 暗色 | 语义 |
|---|---|---|---|
| `--border` | `rgb(242 242 242)` | `rgb(38 38 38)` | 默认弱边框 |
| `--border-shallow` | `rgb(247 247 247)` | `rgb(26 26 26)` | 极浅分隔 |
| `--border-deep` | `rgb(217 217 217)` | `rgb(64 64 64)` | 强边框 |
| `--input` | `rgb(229 229 229)` | `rgb(64 64 64)` | 输入控件边框 |
| `--ring` | `rgb(115 115 115)` | `rgb(82 82 82)` | 焦点环 |
| `--fill` | `rgb(255 255 255)` | `rgb(23 23 23)` | 基础填充 |
| `--fill-default` | `rgb(0 0 0 / 4%)` | `rgb(0 0 0 / 4%)` | 默认覆盖填充 |
| `--fill-shallow` | `rgb(245 245 245)` | `rgb(38 38 38)` | 浅填充 |
| `--fill-deep` | `rgb(0 0 0 / 10%)` | `rgb(0 0 0 / 10%)` | 深覆盖填充 |
| `--mask` | `rgb(0 0 0 / 60%)` | `rgb(0 0 0 / 60%)` | 遮罩 |
| `--spotlight` | `rgb(0 0 0 / 80%)` | `rgb(0 0 0 / 80%)` | 聚光覆盖层 |

暗色透明填充是否需要改为白色叠加由后续实际页面 Review 决定。第一阶段以来源主题为准，不提前设计新值。

### 5.6 辅助基础色

```text
--black
--white
--neutral
```

这些 Token 在暗色模式中可能反转语义。业务代码应优先使用 foreground/background 语义 Token，只有覆盖层计算等底层场景才使用辅助基础色。

- 组件自身局部 CSS 变量，例如布局宽度或 Viewer 内部状态变量；
- 文件格式、语法高亮和第三方渲染器必要的固定主题配置。

## 8. UnoCSS 新接口

UnoCSS 使用共享颜色命名空间，一个颜色键理论上可以生成 `text-*`、`bg-*`、`border-*`。因此必须以语义命名减少误用。

推荐新接口：

```text
bg-background
bg-card
bg-popover
bg-secondary
bg-muted
bg-accent

text-foreground
text-foreground-secondary
text-foreground-tertiary
text-foreground-quaternary
text-primary-foreground
text-brand
text-link
text-destructive

bg-primary
bg-brand
bg-secondary-brand
bg-destructive
bg-success
bg-warning

border-border
border-input
border-border-shallow
border-border-deep
ring-ring
```

禁止因为 UnoCSS 能生成就使用语义错误的组合，例如：

```text
text-secondary   # secondary 是背景 Token
text-muted       # muted 是背景 Token
bg-foreground    # foreground 是文字 Token
```

第一阶段不增加额外抽象来强制区分 utility 类型；通过命名、Review 和后续静态检查约束。只有误用持续发生时才增加 ESLint 或自定义扫描规则。

全局 border preflight 改为使用：

```css
border-color: var(--border);
```


不得继续维护一套与 CSS Token 不一致的橙色 Primary。

## 11. 明暗模式统一

### 11.1 唯一项目主题状态

项目主题由 `<html>` 的属性控制：

```html
<html data-theme="light">
<html data-theme="dark">
```

Arco 同步使用：

```html
<body arco-theme="light">
<body arco-theme="dark">
```

不引入 `.dark` class 作为第三套状态。

### 11.2 首屏初始化

当前 `src/renderer/index.html` 强制设置亮色，与 `useTheme.ts` 的亮色、暗色、跟随系统能力冲突。

第一阶段应：

1. 删除强制亮色脚本和误导性注释；
2. 在首屏可执行的最小脚本中读取 `__sudowork_theme`；
3. 缓存有效时同步设置 `data-theme` 和 `arco-theme`；
4. 缓存无效时根据系统主题设置首屏值；
5. React 初始化后再读取持久化偏好并校正；
6. 保证 `<html>` 和 `<body>` 不出现长期主题不一致。

### 11.3 无效 `dark:` utility

项目没有维护 `.dark` class，因此现有 `dark:` utility 不能可靠响应主题。

已知需要迁移的文件：

```text
src/renderer/layouts/components/UpdateModal.tsx
src/renderer/pages/settings/about/index.tsx
src/renderer/pages/conversation/preview/components/renderers/SelectionToolbar.tsx
```

迁移时使用新语义 Token，不为这几处额外维护 `.dark` class。

## 12. 实施阶段

### 阶段一：基础设施硬切

涉及文件：

```text
src/renderer/styles/variables.css
src/renderer/styles/index.css
src/renderer/styles/arco-override.scss
src/renderer/styles/base.css
src/renderer/index.ts
src/renderer/index.html
src/renderer/hooks/useTheme.ts
uno.config.ts
```

必要时同时处理 3 个使用无效 `dark:` utility 的文件。

步骤：

1. 使用新规范 Token 重写 `variables.css` 的颜色部分；
2. 保留布局、尺寸、圆角、间距、字号和阴影 Token；
3. 删除所有旧项目颜色 Token；
4. 删除旧 UnoCSS 颜色接口；
5. 建立新 UnoCSS 接口；
6. 从新 Token 重建 Arco 桥接；
7. 将 Arco ConfigProvider Primary 改为中性 Primary；
8. 修复首屏主题初始化；
9. 清理无效 `dark:` utility；
10. 运行格式化、类型检查和测试；
11. 生成旧引用清单，不在本阶段顺手修完所有页面。

阶段一允许视觉回归，但不允许：

- 应用无法启动；
- TypeScript 或构建失败；
- 主题切换逻辑抛出异常；
- 输入不可见到无法完成基本操作；
- 安全、数据保存或可访问性基础能力被删除。

### 阶段二：生成并分类迁移债务

旧变量扫描：

```bash
rg --glob '*.{css,scss,ts,tsx}' \
  -- '--(bg-[1-6]|bg-base|bg-faint|bg-subtle|bg-muted|bg-control|bg-emphasis|bg-strong|text-secondary|text-tertiary|text-disabled|border-default|border-light|border-tiny|danger|info|ui-accent-orange|aou-|retroma-|message-|color-guid-agent-bar)' \
  src/renderer
```

业务代码中的 Arco Token 扫描：

```bash
rg --glob '*.{css,scss,ts,tsx}' \
  -- '--color-(bg|text|fill|border)-|--primary-6' \
  src/renderer \
  -g '!styles/arco-override.scss'
```

旧 utility 扫描：

```bash
rg --glob '*.{ts,tsx}' \
  '(^|[[:space:]''"`])(bg-[1-6]|bg-base|bg-subtle|bg-muted|bg-control|text-secondary|text-tertiary|border-light|border-default|bg-fill-[0-4])([[:space:]''"`:]|$)' \
  src/renderer
```

硬编码颜色扫描：

```bash
rg --glob '*.{css,scss,ts,tsx}' \
  '#[0-9a-fA-F]{3,8}|rgba?\(|hsla?\(' \
  src/renderer
```

扫描结果按功能区域归档，不按 Token 名单独开大量零散任务。

### 阶段三：按功能区域 Review 与修复

建议顺序：

1. App Shell、标题栏、侧边栏；
2. 登录和模式选择；
3. 会话主界面；
4. 设置页面；
5. 团队、Cron 和渠道；
6. Workspace 和 Task Panel；
7. 消息、Markdown 和工具调用；
8. Preview、编辑器、终端和图表；
9. Avatar 等独立 Renderer。

每个区域同时完成：

- 旧 Token 引用迁移；
- 业务代码中的 Arco Token 迁移；
- 硬编码主题色迁移；
- 重复 CSS 和无效 selector 清理；
- 不再需要的组件专用 Token 和效果删除；
- 亮色、暗色和主题切换检查；
- Arco Portal、Shadow DOM、Canvas 或第三方渲染器检查；
- 必要的最小回归测试。

不要只把旧变量名批量换成新变量名而跳过功能 Review。

### 阶段四：隔离渲染器收尾

重点包括：

- `src/renderer/components/Markdown.tsx` 的 Shadow DOM Token 注入；
- `src/renderer/styles/markdown.css`；
- xterm 创建后主题更新；
- CodeMirror 主题；
- SyntaxHighlighter 和 diff2html；
- ECharts 读取 CSS Token 后的主题刷新；
- Excel Viewer 注入样式；
- Webview/iframe 内部文档；
- 扩展主题残留代码和示例。

这些区域不能依靠普通 CSS 继承完成迁移，需要分别验证。

## 13. 旧用法迁移参考

下表只用于 Review 时辅助判断，不代表可执行全局替换：

| 旧用法 | 候选新 Token | 必须确认的问题 |
|---|---|---|
| `--bg-base` | `--background` | 是否真的是页面基础背景 |
| `--bg-1` | `--background` / `--secondary` | 是页面、侧栏还是区域底色 |
| `--bg-2` | `--secondary` / `--muted` | 是次级容器还是弱背景 |
| `--bg-3` | `--accent` / `--border-deep` | 是填充还是错误地用背景色充当边框 |
| `--bg-control` | `--fill-shallow` | 是否属于输入或控件填充 |
| `--text-secondary` | `--foreground-secondary` | 是否仍需足够对比度 |
| `--text-tertiary` | `--foreground-tertiary` | 是否是提示或禁用状态 |
| `--text-disabled` | `--foreground-quaternary` | 元素是否同时需要禁用交互语义 |
| `--border-default` | `--border` / `--input` | 是普通边框还是输入框边框 |
| `--border-light` | `--border` / `--border-shallow` | 分隔线需要多弱 |
| `--border-tiny` | `--border-shallow` | 浅色和暗色是否仍可见 |
| `--danger` | `--destructive` | 是否真的是破坏性或错误状态 |
| `--info` | `--link` / `--blue` | 是链接、信息提示还是数据系列 |
| `--ui-accent-orange` | `--brand` / `--primary` | 是品牌强调还是主要操作 |
| `--brand-light` | `--secondary-brand` | 是否是品牌弱背景 |
| `--color-bg-*` | 背景语义 Token | 业务代码不应继续引用 Arco 层级 |
| `--color-text-*` | 前景文字 Token | 选择具体文字层级 |
| `--color-fill-*` | `--fill-*` | 是实体填充还是透明叠加 |

## 14. 中文注释规范

Token 文件统一使用以下分类：

```css
/* 新规范 Token：背景 */
/* 新规范 Token：前景文字 */
/* 新规范 Token：品牌色 */
/* 新规范 Token：功能色 */
/* 新规范 Token：边框、填充与覆盖层 */
/* 项目扩展 Token：布局与尺寸 */
/* 项目扩展 Token：圆角、间距、字号与阴影 */
/* 第三方 Arco 桥接：业务代码禁止直接使用 */
```

不再使用：

```text
旧 Token 兼容别名
LEGACY ALIAS
NEW
THIRD-PARTY
```

因为硬切方案没有兼容别名，英文分类标记也不符合本次约定。

普通业务注释仍遵循项目现有规范；本方案只规定 Token 分类和主题桥接注释使用中文。

## 15. 风险与应对

### 15.1 CSS 缺失不会自动报错

风险：删除 Token 后，CSS 声明静默失效，不会由 TypeScript 或测试自动发现。

应对：

- 阶段一后立即运行静态扫描；
- 按功能区域做明暗模式视觉 Review；
- 对关键交互增加最小 UI 回归检查；
- 不以“编译通过”作为迁移完成标准。

### 15.2 Arco 与项目主题不同步

风险：`data-theme` 和 `arco-theme` 短暂或长期不一致，导致页面与弹层颜色不同。

应对：

- 主题应用函数统一设置两个属性；
- 首屏脚本同步设置两个属性；
- ConfigProvider Primary 从同一 resolved theme 得出；
- 检查 Modal、Popover、Message、Select 下拉等 Portal 组件。

### 15.3 UnoCSS 旧 class 静默消失

风险：删除规则后旧 class 不生成 CSS，但 JSX 本身不会报错。

应对：

- 使用静态扫描建立债务清单；
- 页面 Review 时检查 class；
- 迁移稳定后再考虑加入禁止旧 class 的 lint/check 脚本，当前不提前增加工具。

### 15.4 隔离渲染器不继承普通 CSS

风险：Shadow DOM、Canvas、xterm、ECharts、第三方主题对象不会自动跟随新 Token。

应对：

- 独立放到阶段四；
- 对每个渲染器检查初始化和主题切换两条路径；
- 从 `getComputedStyle` 读取新 Token 时保证主题变化后重新应用。

### 15.5 扩展主题兼容性

风险：历史扩展主题可能覆盖已删除的旧 Token，从而不再生效。

应对：

- 本次明确不承诺旧扩展主题兼容；
- 后续 Review 扩展主题加载链路和示例；
- 如果恢复扩展主题能力，扩展只能覆盖新规范 Token，并需要版本或能力声明。

## 16. 验证方案

### 16.1 阶段一基础检查

```bash
bunx prettier --check \
  src/renderer/styles/variables.css \
  src/renderer/styles/index.css \
  src/renderer/styles/arco-override.scss \
  src/renderer/styles/base.css \
  src/renderer/index.ts \
  src/renderer/index.html \
  src/renderer/hooks/useTheme.ts \
  uno.config.ts

bunx eslint <本次修改的 TS/TSX 文件> --fix
bunx tsc --noEmit
bun run test
```

### 16.2 主题基础验收

- 亮色、暗色和跟随系统均可切换；
- 冷启动首屏不被固定为亮色；
- `<html data-theme>` 与 `<body arco-theme>` 始终一致；
- Arco Primary 按钮亮色为黑底白字，暗色为浅色底深色字；
- Arco Modal、Popover、Message 和 Select 下拉与页面主题一致；
- 当前字体栈不变；
- 旧项目 Token 不再定义；
- 旧 UnoCSS 颜色接口不再生成；
- 应用仍可启动并完成基本导航。

### 16.3 硬切完成条件

阶段一完成不等于全站视觉迁移完成。阶段一完成条件是：

1. 新规范 Token 已成为唯一项目颜色来源；
2. 旧项目 Token 定义和兼容别名为零；
3. Arco 桥接只从新 Token 派生；
4. 旧引用清单已生成并可按功能区域推进；
5. 基础构建、类型检查和测试通过；
6. 已知视觉回归被接受并进入后续 Review，而不是用兼容层掩盖。

全站迁移完成条件是：

1. 业务代码中的旧 Token 引用为零；
2. 业务代码中的 Arco Token 直接引用为零；
3. 旧 UnoCSS class 使用为零；
4. 主题相关硬编码颜色已逐项审查；
5. 所有主要功能区域完成亮色和暗色 Review；
6. Markdown、终端、编辑器、预览器和图表完成主题切换验证；
7. 不再需要的组件专用主题代码已删除。

## 17. 预期结果

硬切后，页面短期内会暴露视觉缺陷，但主题系统不再维持两套项目接口。后续每个功能区域的 Review 都会同时完成 UI Token 迁移、硬编码清理和样式精简，最终形成：

- 一套项目规范 Token；
- 一层受控的 Arco 第三方桥接；
- 一套与新 Token 对齐的 UnoCSS 接口；
- 一条明确的明暗模式状态链路；
- 无旧 Token、无兼容别名、无隐藏迁移债务的 Renderer 样式体系。
