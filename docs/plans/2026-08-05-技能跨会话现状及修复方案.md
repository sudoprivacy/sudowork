# 技能跨会话现状及修复方案

## 1. 问题场景

用户在会话 A 中要求 Scode 新增一个 Skill。完成后再次询问 Skill 列表，会话 A 能看到新增 Skill；新建会话 B 后再次询问，列表中不再包含该 Skill。

用户预期是：

> “新增 Skill”默认表示安装为当前用户可长期使用的能力，而不是只在当前会话临时可见。

## 2. 当前架构

### 2.1 用户级 Skill 库

Sudowork 的用户级 Skill 根目录为：

```text
~/.nexus/skills/
```

个人模式主要分为：

```text
~/.nexus/skills/
├── _system/
├── _hub/
└── _my-custom-skill/
```

其中用户自定义 Skill 的目标目录是：

```text
~/.nexus/skills/_my-custom-skill/<skill-name>/
```

相关代码：

```text
src/process/initStorage.ts
src/process/SkillManager.ts
```

### 2.2 会话 Workspace 中的 Skill 目录

Scode 会话实际使用：

```text
<workspace>/.nexus/sudocode/skills/
```

该目录通常不是用户级 Skill 的真实存储位置，而是由 Sudowork 将当前会话允许使用的 Skill 链接进来。

相关代码：

```text
src/process/utils/workspaceSkillsDir.ts
src/process/utils/workspaceSkillTargets.ts
src/process/bridge/conversationBridge.ts
```

### 2.3 会话创建时的同步

新建 Scode 会话后，Sudowork 会：

1. 获取当前用户已安装的 Skills；
2. 根据当前助手的 `enabledSkills` 等配置筛选；
3. 在当前 Workspace 的 `.nexus/sudocode/skills/` 下创建符号链接；
4. 首条消息向 Agent 注入可用 Skill 名称及路径。

因此，会话中的“可见 Skill”实际由两部分共同决定：

```text
用户级是否已安装
+
当前助手/当前会话是否允许使用
```

### 2.4 会话中生成 Skill 后的提升逻辑

Turn 结束时，`AcpAgent` 会尝试识别本轮生成的 Skill，并安装到用户自定义 Skill 目录：

```text
src/process/task/AcpAgent.ts
  → installTrackedWorkspaceSkills()
  → installWorkspaceSkillsFromTrackedFiles()
```

具体安装逻辑位于：

```text
src/process/task/workspaceSkillInstaller.ts
```

候选 Skill 通常必须满足：

- 存在有效的 `SKILL.md`；
- 存在 `_sudowork_meta.json` 或兼容元数据；
- 生成过程被当前 Turn 文件追踪捕获；
- Skill 根目录没有被忽略；
- Turn 正常结束并执行安装阶段。

安装成功后目标应为：

```text
~/.nexus/skills/_my-custom-skill/<skill-name>/
```

## 3. 当前问题

### 3.1 “当前会话可见”不等于“已安装”

如果 Scode 将 Skill 直接写到：

```text
<workspace>/.nexus/sudocode/skills/<skill-name>/
```

当前会话可以立即扫描并列出它，但它仍属于当前 Workspace。

新会话使用新的 Workspace，只会重新同步用户级已安装 Skills，因此不会包含该临时 Skill。

### 3.2 自动提升存在识别盲区

`workspaceSkillInstaller.ts` 的普通候选扫描会忽略 `.nexus` 等隐藏目录，避免把系统同步目录误当作用户交付物。

因此，直接写入：

```text
<workspace>/.nexus/sudocode/skills/
```

的 Skill 可能不会进入用户级安装流程。

Scode 也可能把自定义 Skill 写到沙盒 Home：

```text
<workspace>/.sandbox-home/.nexus/skills/_my-custom-skill/
```

Sudowork 已有针对该位置的提升逻辑，但仍依赖完整元数据和 Turn 正常收尾。

### 3.3 Skill 包格式不完整时会跳过安装

如果只有 `SKILL.md`，但缺少 `_sudowork_meta.json`，当前安装器可能将其判定为不完整 Skill 包并跳过。

Agent 的自然语言回复可能仍然声称“已新增”或“已安装”，造成产品状态与文件系统状态不一致。

### 3.4 安装与启用没有形成闭环

即使 Skill 已复制到用户级目录，新会话是否可见仍可能受以下条件影响：

- 当前助手的 `enabledSkills` 白名单；
- Skill 是否被禁用；
- Skill ID 与名称映射是否成功；
- 新会话 Skill 链接同步是否完成；
- `AcpSkillManager` 缓存是否已重置。

当前“安装成功”与“当前助手后续会话可用”不是同一个状态。

### 3.5 用户提示缺少明确状态

当前产品没有清楚区分：

```text
已生成 Skill 包
已安装到用户 Skill 库
已对当前助手启用
已同步到当前会话
```

用户看到“新增成功”时，会自然理解为后续会话也可用，但实际可能只完成了第一步。

## 4. 根因

> Sudowork 已具备用户级 Skill 库和 Workspace Skill 同步能力，但“会话中生成 → 用户级安装 → 当前助手启用 → 新会话同步”的闭环不够可靠，并且缺少统一、可验证的成功语义。

这主要是 Sudowork 的 Skill 集成问题，不是 Scode Session 遗忘问题。

## 5. 修复目标

1. 用户说“新增/创建并使用一个 Skill”时，默认安装到用户级 Skill 库。
2. 只有文件真实安装成功后，才能回复“已安装”。
3. 安装成功后，同一助手的新会话必须可见。
4. 明确区分“只生成 Skill 包”和“安装 Skill”。
5. 不依赖某个模型恰好选择正确目录。
6. 不把 Workspace Skill 同步目录当作用户级真实存储。

## 6. 推荐修复方案

### 6.1 统一安装入口

不要让模型自行决定最终安装目录。无论 Skill 在本轮生成到哪里，最终都必须经过 Sudowork 的受控安装函数：

```text
生成 Skill 包
→ 校验
→ 安装到用户级目录
→ 更新启用状态
→ 重新同步 Workspace
→ 验证
→ 返回成功消息
```

唯一用户级目标：

```text
~/.nexus/skills/_my-custom-skill/<skill-name>/
```

### 6.2 扩大候选发现，但排除已管理链接

候选发现需要覆盖：

- Workspace 中普通生成目录；
- `.sandbox-home/.nexus/skills/_my-custom-skill/`；
- Scode 直接创建的新 Workspace Skill 目录。

扫描 `.nexus/sudocode/skills/` 时必须区分：

- Sudowork 创建的既有符号链接：跳过；
- 本轮新建的真实目录：允许作为安装候选；
- 指向用户级 Skill 库的链接：不得反向复制。

### 6.3 安装前强校验

至少验证：

- Skill 根目录存在；
- `SKILL.md` 存在；
- frontmatter 包含有效 `name` 和 `description`；
- 目录名与 Skill 名称可安全映射；
- 元数据合法；
- 不包含越界路径或危险符号链接；
- 目标路径位于用户自定义 Skill 根目录内。

缺少可自动补齐的展示元数据时，可以由 Sudowork 从 `SKILL.md` 生成最小 `_sudowork_meta.json`，不要因纯展示字段缺失而悄悄丢弃有效 Skill。

### 6.4 安装后自动启用当前助手

推荐语义：

> 用户在某助手会话中明确要求创建并安装 Skill 时，安装成功后自动加入该助手的启用列表。

不自动修改其他助手，避免扩大能力范围。

如果当前助手没有白名单限制，则保持现有“所有已启用用户 Skill 可用”的行为。

### 6.5 安装后立即同步并验证

安装完成后依次执行：

1. 清理 Skill 内容缓存；
2. 重置 `AcpSkillManager`；
3. 更新当前助手/Conversation 的启用列表；
4. 重新执行 Workspace Skill 同步；
5. 验证当前 Workspace 的链接存在；
6. 验证用户级目标 `SKILL.md` 存在；
7. 新建会话时再次通过同步逻辑验证可见性。

### 6.6 修正用户提示

建议状态文案：

```text
已生成 Skill 包：<path>
```

```text
已安装并对当前助手启用：<skill-name>
```

```text
Skill 已生成，但安装失败：<可操作原因>
```

禁止在未验证目标文件存在时输出“已安装”。

## 8. 验收场景

### 8.1 当前会话创建并安装

```text
会话 A：帮我创建并安装测试 Skill。
```

预期：

- 用户级自定义 Skill 目录存在；
- 当前会话 Skill 列表包含它；
- 回复明确显示“已安装并对当前助手启用”。

### 8.2 新会话可见

```text
新建同一助手的会话 B：列出 Skill。
```

预期：包含会话 A 安装的 Skill。

### 8.3 只生成不安装

```text
只帮我生成 Skill 包，不要安装。
```

预期：

- 只产生交付目录或压缩包；
- 用户级 Skill 库不变化；
- 回复不得声称已安装。

### 8.4 不完整 Skill

创建缺少元数据或 frontmatter 的 Skill。

预期：自动补齐可安全补齐的字段，或明确返回校验错误；不得静默跳过后仍回复成功。

### 8.5 助手白名单

在助手 A 中安装 Skill，随后分别新建助手 A 和助手 B 会话。

预期：

- 助手 A 可见；
- 助手 B 不自动启用，除非其策略允许全部用户 Skills。

## 9. 非目标

本修复不处理：

- 聊天上下文跨会话继承；
- 用户长期记忆；
- 项目管理；
- Remote/Moss 服务器端 Skill 存储；
- Skill Hub 发布审批。

这些能力与本地 Skill 安装闭环分开实施。
