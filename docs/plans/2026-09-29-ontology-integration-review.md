# Sudowork 本体工作台重设计方案（Review v3）

日期：2026-09-29。状态：首期代码已实施并完成验证；详见文末实施记录。

本版按用户最新意见重新组织：以使用合理性为先，菜单、页面、交互和本体数据结构均可重做；不承担旧本体工作台的数据兼容与迁移。保留已经确定的标准 `.rdf` / `.owl` 导入导出、重点建设图编辑器，以及工作台内左对话、右本体的工作方式。底层会话继续使用 Sudowork，但本体会话不显示在普通会话列表中。

## 1. 设计原则与范围

### 1.1 按用户任务设计

本体工作台服务四类连续任务：建立和理解业务模型、把模型连接到资料或数据、验证模型及能力、导出或发布供其他工具与助手使用。菜单围绕这些任务组织，不按现有包、表、服务或旧页面划分。

采用两层结构：**本体库负责选本体，一份本体的工作区负责做事情。** 图编辑器是建模主界面；对话是工作区内的协作方式。数据表、函数编辑和版本审查各有合适的页面空间。

默认先让用户看懂当前本体、下一步可做什么、修改是否保存。连接参数、IRI、公理、执行日志等按任务和上下文展开，避免同时占据画布。

### 1.2 本次明确放开的约束

| 项目                             | 本版决定                                                                                              |
| -------------------------------- | ----------------------------------------------------------------------------------------------------- |
| 旧菜单及页面                     | 可以全部替换；不保留“连接 / 资产 / AI 构建 / 本体 / 发布 / Agent”原有导航约束                         |
| 旧本体数据结构与数据库           | 可采用新的领域模型、表结构及存储方式，依据标准文件交换和图编辑需要设计                                |
| 旧本体数据、版本、映射及会话关联 | 不迁移、不做兼容读取，不要求新系统恢复旧工作台状态                                                    |
| 旧本体 API 与组件                | 按质量和适配成本决定复用或替换，不维护仅服务旧工作台的兼容层                                          |
| 新工作台自身的数据               | 必须正确保存、恢复、版本化；“不兼容旧数据”不降低新系统的数据完整性要求                                |
| Sudowork 公共平台                | 继续复用会话、模型、附件、权限确认、连接器执行和助手/MCP 交付等适合的能力；普通会话及其他功能不受影响 |

本次仅更新方案和评审草图，不执行旧数据清理。实现时旧本体存储不参与新系统启动，建立清晰的新数据边界；无需为旧数据设计迁移产品流程。

## 2. 信息架构：本体库 + 本体工作区

### 2.1 本体库

从 Sudowork 的“本体工作台”入口进入本体库。页面只处理本体的选择与生命周期，提供搜索、最近打开、本体列表、“新建本体”和“导入本体”。列表显示名称、说明、最近修改和发布状态，不放与当前任务无关的统计看板。

新建空白本体只要求名称；业务目标、数据来源和会话可以稍后补充。导入标准文件后允许修订名称，预览通过即可进入图编辑器。纯本体建模不强制先配置数据源或模型。

重命名、归档/删除等低频操作位于每份本体的更多菜单。进入本体后有明确的“返回本体库”和本体切换入口。

### 2.2 一份本体内的五个工作区页面

| 导航     | 用户来这里做什么                 | 主内容                                              | 页面主要操作                                     |
| -------- | -------------------------------- | --------------------------------------------------- | ------------------------------------------------ |
| **建模** | 创建、理解、调整本体             | 左侧本体对话，右侧图编辑器；选中时展开对象/关系详情 | 新增对象、连线、编辑属性、保存                   |
| **数据** | 给当前本体添加资料并建立映射     | 当前本体的数据源和文档、预览、字段映射              | 添加来源、预览、建立/调整映射                    |
| **能力** | 定义本体可以查询、计算或执行什么 | 查询/函数/动作列表，参数、实现、测试结果            | 创建能力、编辑、试运行                           |
| **检查** | 处理问题并判断是否可交付         | 未解决业务问题、结构/映射/能力检查及结果            | 运行检查、回答问题、定位并修正                   |
| **发布** | 管理版本并交付使用               | 工作稿差异、候选版本、已发布版本和使用入口          | 创建版本、审查发布、导出、创建助手/取得 MCP 配置 |

五项是同一份本体的页面导航。页内保留本体身份和保存状态，切页不改变会话归属或后台任务范围。

### 2.3 原有能力的新归属

| 能力                         | 放在哪里                                                    | 原因                                                      |
| ---------------------------- | ----------------------------------------------------------- | --------------------------------------------------------- |
| AI 构建                      | 建模页左侧对话                                              | 用户能直接看到 AI 正在修改的模型，无需单独“AI 构建”页面   |
| 连接与资产                   | 数据页的“添加来源 → 选择已有连接 / 新建连接 → 选择资料”流程 | 让用户一次完成给当前本体提供资料，避免在多个管理页跳转    |
| 可复用连接管理               | 数据页中的连接管理入口，按需打开独立对话框/面板             | 属于来源配置，不与本体建模争夺一级导航                    |
| 对象、属性、关系             | 建模页的图/结构两种视图和选中详情                           | 同一模型的不同查看方式，不拆成互不关联的页面              |
| 证据                         | 模型详情、对话结果和检查条目的来源链接                      | 证据在解释某个结论时最有价值，无需常驻一级菜单            |
| 业务问题、验证失败、来源漂移 | 检查页的待处理事项，并反向定位模型/来源/能力                | 用户只需一个明确的问题处理入口                            |
| 版本历史与差异               | 发布页                                                      | 用户在决定交付和切换版本时查看                            |
| Agent、MCP、服务交付         | 发布页选定版本后的“使用此版本”区域                          | 交付依赖已发布模型，不要求用户单独理解一套 Agent 管理导航 |
| 执行记录                     | 对应能力详情                                                | 与被运行的能力及具体版本直接关联                          |
| 本体 IRI、命名空间等         | 本体名称旁的设置入口，必要时从导入/编辑详情直达             | 配置低频，但要可发现；不常驻主画布                        |

## 3. 页面布局与使用路径

### 3.1 建模页：默认左对话、右图

```text
← 本体库    订单交付本体 ▾                       已保存    文件 ▾
            建模    数据    能力    检查    发布
┌────────────────────────────┬──────────────────────────────────────────┐
│ 本体对话  当前会话 ▾  新建  │ 图 / 结构        新增对象 · 连线 · 搜索   │
│                            │                                          │
│ 消息、工具结果、业务问题    │                  本体图                  │
│ AI 修改建议与进度          │                                          │
│                            │       选中节点后按需展开详情              │
│ 输入框、附件、模型、停止    │                                          │
│                            │ 检查结果/修改摘要（需要时展开）            │
└────────────────────────────┴──────────────────────────────────────────┘
```

默认左侧约 35%、右侧约 65%，可拖动分隔线。对话可折叠，图可临时最大化。画布内的对象详情仅在选中时展开，允许收起；检查结果和修改摘要按需展开，避免常驻四栏。

“图 / 结构”是同一份模型的两种视图。图用于关系理解和编辑，结构视图用于查找、批量查看属性及浏览复杂公理。两者共享选择、搜索和修改状态。

“文件”统一提供导入、导出及标准文本预览；建模页主操作聚焦编辑和保存，不把连接管理、能力试运行、发布表单都放到图工具栏。

左侧会话历史通过下拉框/抽屉管理，不再增加常驻历史列表。本体与会话是一对多关系：切换历史会话只切换消息，右侧仍是当前工作稿；查看历史模型必须到发布页显式选定版本。

### 3.2 其他页面按任务安排空间

数据、能力、检查、发布采用各自适合的列表、表格、编辑区或差异视图，不嵌套在图编辑器的小标签面板里。数据密集页面默认收起对话，保留“本体对话”按钮；展开时仍在当前工作台左侧，右侧保留当前页面和选中对象。

切回建模恢复用户的分栏宽度、画布位置和选择。用户可在任何页面将当前来源、能力、错误或差异加入对话上下文。会话始终绑定当前本体，绝不跳转到普通聊天页面。

窄窗口在“对话 / 当前工作内容”之间切换，桌面保持左右操作。页面导航、本体名称和运行状态始终可见；不会为了展示完整菜单缩小图中文字。

### 3.3 四条主要用户路径

| 场景             | 路径                                                                  | 用户不必先做的事                |
| ---------------- | --------------------------------------------------------------------- | ------------------------------- |
| 已有标准本体文件 | 本体库导入 → 图预览 → 保存 → 编辑 → 导出                              | 创建 AI 会话、接入数据库        |
| 从业务目标开始   | 新建本体 → 左侧输入目标 → 按需选择资料 → AI 提议修改 → 右图查看与调整 | 学会原有连接/资产/建模多个入口  |
| 手工建模后接数据 | 新建 → 图中创建模型 → 数据页添加来源和映射 → 检查                     | 被迫由 AI 生成模型              |
| 交付给助手使用   | 检查问题 → 发布页审查版本 → 使用此版本 → 创建助手或获取 MCP 接入信息  | 离开当前本体查找对应 Agent/服务 |

流程是可自由进入的工作方式，不设置强制五步向导。标准文件可以在未发布时导出；纯语义本体允许没有业务数据源、函数或动作。

### 3.4 保存、AI 修改与离开页面

人工编辑形成本地修改集，可撤销/重做；显式保存提交一个模型 revision。自动保留本地编辑缓存以支持意外关闭后的恢复，但不把缓存等同于已提交工作稿。

AI 提议修改先写入变更集，标明涉及对象、属性、关系或公理；验证通过后可应用到工作稿并高亮结果。模型写入统一串行化；人工存在未保存修改时，AI 仍可调查或提出建议，应用时进行版本检查和冲突处理，不覆盖本地编辑。

用户可以选择允许当前构建任务自动应用经过检查的草稿变更。该设置不授予发布或执行有副作用动作的权限。默认以可审查修改为入口，避免需要不断暂停才能查看或修正模型。

切换页面不会丢失本地修改；只有离开本体、关闭编辑或应用冲突变更时处理保存/保留问题。拒绝 AI 建议不改变当前模型，已应用变更可通过新的修改恢复。

## 4. 图编辑器：首期核心

### 4.1 必须形成完整编辑能力

| 能力       | 首期要求                                                                                   |
| ---------- | ------------------------------------------------------------------------------------------ |
| 对象与属性 | 画布/结构视图创建对象，编辑名称、说明、类型化属性、标识与来源；区分显示名称、IRI 和内部 ID |
| 关系       | 节点拖拽连线或表单创建；编辑方向、语义、约束和数据连接；区分自关系与平行关系               |
| 继承与公理 | 继承边有明确样式；属性特征、domain/range 和类限制可查看编辑；复杂公理提供结构化详情        |
| 浏览       | 平移、缩放、框选、搜索、定位邻接、筛选、自动布局、节点固定；小地图按规模显示               |
| 编辑历史   | 至少 50 步撤销/重做、快捷键；一次连线或批量操作作为完整历史单元                            |
| 问题定位   | 悬空引用、IRI 冲突、约束问题定位到节点、边或属性；删除前展示实际依赖                       |
| AI 联动    | 选中元素可加入对话；已应用变更增量高亮，流式消息不导致整图重排；修改详情可逐项定位         |
| 文件联动   | 导入后可视化检查，编辑后导出标准文件；未显示的公理不因无关编辑丢失                         |

画布布局是呈现状态，不影响模型 revision。显示名称修改不自动改变 IRI；变更 IRI 是独立操作，需要更新引用。

新领域模型明确支持未指定的业务基数、标准约束、共享属性及复合业务标识。OWL 键、公理限制和业务主键分别表达，不因旧字段结构把它们压成同一概念。

### 4.2 渐进呈现

默认画布显示对象和关键关系，不展开所有属性、证据、函数和数据源节点。选中、筛选或切换专门视图时才展示相应信息。

复杂 OWL 表达式首期可在结构视图和详情中只读保留；不能图形编辑不意味着不能导入或导出。实例断言可在详情/表格查看；全量实例知识图谱不是首期画布范围。

图规模较大时采用局部展开、层次布局和筛选，而非通过缩小字体塞入全图。建立小、中、大样本的布局/交互基线，保持输入和页面导航可响应。

## 5. 标准 .rdf / .owl 导入导出：首期必做

### 5.1 明确语法范围

以 RDF 1.1 和 OWL 2 为兼容基线。文件扩展名不替代内容识别：RDF/XML 是 RDF 的 XML 表达，也是 OWL 2 的主要交换语法；OWL/XML 使用不同语法处理器。[RDF/XML 规范](https://www.w3.org/TR/rdf-syntax-grammar/)、[OWL 2 语法概览](https://www.w3.org/TR/owl2-overview/)

| 文件 / 语法             | 支持范围                                                      |
| ----------------------- | ------------------------------------------------------------- |
| `.rdf`，RDF/XML         | 首期标准导入与导出                                            |
| `.owl`，RDF/XML         | 首期标准导入与导出，默认 OWL 交换格式                         |
| `.owl`，OWL/XML         | 首期标准导入与导出，按 OWL 2 公理结构处理                     |
| Turtle 等其他语法       | 可按真实交换需求扩展；不因为旧入口存在而成为本次兼容义务      |
| Functional / Manchester | 首期不承诺完整编解码；识别后明确说明，不能误读成 XML 或空模型 |

### 5.2 导入与导出流程

导入分为本体库的“导入新本体”和工作区文件菜单的“合并到当前本体”。流程为文件选择、语法解析、图/结构预览、语义及依赖报告、冲突处理、原子提交。默认不替换整个工作稿，失败或取消不产生部分修改。

按完整 IRI 与实体种类匹配，避免同名不同命名空间被合并；相同定义重复导入保持幂等。`owl:imports` 保留声明，支持为依赖指定本地文件或已配置来源，未解析依赖有明确状态。

导出允许选择已保存工作稿、包含未保存编辑的预览稿，或新系统内某个发布版本，明确标注范围。标准文件交换与发布独立；导出不要求创建助手或完成业务数据映射。

保留 IRI、空白节点、集合、类型化字面量、语言标签、实例断言与复杂公理。导出 OWL/XML 前检查完整可表达性，任意 RDF 图不应强行转换成 OWL 2 结构；不能完整表达时说明原因并保留 RDF/XML 路径。[OWL 2 RDF 映射](https://www.w3.org/TR/owl2-mapping-to-rdf/)、[OWL/XML 规范](https://www.w3.org/TR/owl2-xml-serialization/)

### 5.3 标准语义与业务扩展

标准文件输出标准本体语义。聊天、凭据、函数脚本、执行配置和图布局不自动写入标准文件；完整工程包单独设计。标准语义的往返保留属于首期要求，不能用工程包代替。

解析采用标准编解码器，不沿用当前正则抽取少量 Class/ObjectProperty 的实现。核心映射涵盖类、对象/数据/注解属性、类/属性继承、标签/注释、domain/range、逆属性、属性特征和常用限制。复杂表达式、属性链、公理注解及未知词汇保留在标准语义层。

不能将 `rdfs:domain/range` 自动当作业务数据校验条件，或给没有声明的基数填入猜测值。新模型从一开始表达这类差异。标准文件可解析和业务规则检查通过，不等同于已执行完整 OWL 逻辑推理。

采用独立解析器、RDF 图同构/OWL 公理比较及外部编辑器样例验证往返结果，不只做同一实现的自读自写。比较语义，不要求 XML 空白、前缀、元素顺序或空白节点编号逐字相同。

## 6. 新领域模型与公共能力边界

### 6.1 从标准语义与编辑任务出发设计新数据

不保留旧本体表结构作为前提。新领域聚合以一份本体为边界，包含以下职责：

| 领域内容           | 职责                                                                   |
| ------------------ | ---------------------------------------------------------------------- |
| 本体与语义文档     | 本体 IRI、命名空间、RDF 图/OWL 公理、导入来源及依赖                    |
| 类型化编辑视图     | 对象、属性、关系及可编辑约束，从标准语义映射而来；支撑快速检索与图交互 |
| 数据绑定           | 本体引用的来源、字段映射和业务标识；运行时凭据由公共连接器管理         |
| 能力定义           | 查询、函数、动作、参数、实现绑定和试运行记录                           |
| 变更集             | 操作、来源（人工/AI/导入）、基线 revision、检查结果和应用状态          |
| 本体会话与构建任务 | 关联公共 conversationId、当前目标和任务状态；不复制公共消息数据        |
| 问题、证据与检查   | 业务决定、来源依据、依赖及可定位的验证结果                             |
| 版本与交付         | 冻结的语义及业务定义、差异、验证记录和助手/MCP 使用关系                |
| 呈现状态           | 布局、选择、分栏、视图及本地编辑缓存，与模型内容分开                   |

标准公理以语义文档为准，类型化编辑视图作为可重建投影，业务执行扩展有明确独立归属；通过同一命令事务协调更新，禁止两份模型独立保存后互相覆盖。共享属性、同 IRI 不同实体用途、复杂公理和未指定约束按新模型直接支持。

### 6.2 复用公共会话，新增业务用途

现有 `conversation.type` 的 `acp` / `remote-agent` 表示运行类型。新本体会话沿用实际运行类型，新增用途与归属元数据，例如 `extra.purpose = 'ontology'`、`extra.ontologyId`。普通会话缺省归类 `general`，不改变其历史或运行方式。

本体会话从创建起就带用途标记。普通列表、其搜索/置顶/分组/标签恢复按 general 查询；本体内部历史按 ontologyId 查询。用途在服务端查询/分页/计数层处理，前端采用一致规则；底层维护、备份及工作空间清理仍能看到适用的全部会话。

按 conversationId 发送、停止、恢复、读取消息和附件继续复用公共服务。路由和通知指向本体内部位置，例如 `/app/ontology/:ontologyId/model?sessionId=...`。嵌入消息和输入组件，不挂载普通会话页面外壳与普通标签管理器。

新会话与新本体关联的创建、运行中断和删除应幂等、可恢复。删除会话不删除模型；证据保留必要摘要及关联 ID。旧本体会话的迁移、旧注册表回填及旧本体深链兼容从本次范围中移除。

### 6.3 修改、验证与发布

所有修改显式绑定 ontologyId，携带 expectedRevision、operationId 和变更内容，事务内检查版本并应用。显示名称变化保持 IRI 稳定，标准语义变更纳入 revision；消息、布局、执行次数不递增模型 revision。

检查结果绑定模型内容、来源结构前提、测试定义和时间，修改后相关报告失效。结构错误、业务问题与抽样数据问题分别显示。纯语义本体不因缺少可选业务映射被禁止导出或发布；只有启用具体可执行能力时要求相应绑定及检查就绪。

新发布流程统一为工作稿 → 候选版本 → 审查 → 发布。用户只发布所审查的候选内容，创建候选时原子绑定验证和模型快照。发布冻结模型定义，不承诺冻结外部实时数据。

切换活动发布版本与从历史恢复工作稿是两个明确动作。新助手交付绑定选定版本，更新绑定显式进行；不承担旧工作台版本或蓝图兼容。

## 7. 后续构建闭环与治理

首期左侧对话具备实际构建能力：理解目标、读取选定资料、查询当前模型、提出变更并关联右侧模型；不能只把聊天框放进页面。完整多轮自主循环随后增强。

构建循环围绕调查、澄清、修改、验证、修正和人工交接。记录证据、业务决定、未解决问题、失败报告及预算，复用公共会话历史；重启后恢复领域状态。纯文本“完成”不能绕过当前模型检查和问题处理。

AI 读取和修改使用明确本体范围及分页上下文。自动验证限于允许的读取与检查，业务写入继续由能力执行入口治理。发布和有副作用动作不因允许自动应用草稿变更而自动获准。

来源变化进入检查页待处理事项，关联数据页中的实际差异；能力执行日志在能力详情，版本影响在发布页。后续围绕实际写入场景增加预览、审批、过期检查、幂等及业务事件，避免先建立空的“监控”“策略”一级页面。

## 8. 交付阶段与验收

### 8.1 交付顺序

| 阶段                        | 交付内容                                                                | 验收重点                                                           |
| --------------------------- | ----------------------------------------------------------------------- | ------------------------------------------------------------------ |
| P0：新设计与基础契约        | 完成可点击页面流程；确定新本体语义/业务模型、变更集、用途分类和平台接口 | 任务可找到正确页面；模型支持标准语义；无旧表/旧入口兼容负担        |
| P1A：工作区骨架与真实对话   | 本体库、五页导航、建模左右布局、用途过滤、内部会话管理及基础 AI 变更    | 本体对话不进入普通列表；可在当前本体持续对话与修改；切页不串上下文 |
| P1B：主图编辑器             | 对象/属性/关系/继承、画布操作、结构视图、撤销重做、变更审阅和错误定位   | 用户可主要通过图完成建模；AI/人工修改可理解、可恢复且不互相覆盖    |
| P1C：标准文件交换与基本交付 | RDF/XML、OWL/XML 双向交换、预览合并、公理保留、基本检查及版本导出/发布  | 外部标准文件可编辑后交换；新系统版本冻结和文件范围正确             |
| P2：数据能力与构建闭环完善  | 完整数据映射/能力编辑与试运行、业务问题/证据、多轮自主修正和助手交付    | 从目标、资料到可验证能力和已发布助手形成完整路径                   |
| P3：持续治理                | 业务验收用例、来源漂移、细粒度影响、动作审批与执行事件                  | 变化可定位、可修正、可重新验证并明确交付                           |

五个页面的首期最低可用范围分别是：建模可编辑和保存；数据可添加/预览资料并建立基本映射；能力至少可定义和试运行一种只读查询；检查可运行并定位结构/映射问题；发布可创建、审查、导出和发布版本。复杂跨源映射、更多执行器和自主构建循环随后深入。空状态提供真实可执行的下一步，尚未开放的功能不摆放无响应按钮。P1A/B/C 完成才算首期主交付。

### 8.2 首期端到端路径

1. 本体库新建空白本体，立即进入建模；无需先配置数据源或创建聊天。
2. 手工添加对象、属性、关系，撤销/重做并保存；重新打开后内容与布局正确。
3. 导入外部 `.rdf` / `.owl`，检查语义和依赖，合并到图后修改显示名称及关系。
4. 左侧创建专属对话，将选中对象加入上下文；AI 提议的变更可定位、接受或拒绝。
5. 切换数据页选资料、检查页处理问题，再回到建模，图、对话和未保存内容保持合理状态。
6. 普通会话列表及其搜索/置顶/标签不显示本体会话；本体内部历史可以恢复消息和任务。
7. 人工编辑与 AI 提议同时存在时，不丢数据；切换另一份本体后事件和写入范围保持隔离。
8. 分别导出 `.rdf` RDF/XML、`.owl` RDF/XML 和可表达的 `.owl` OWL/XML，经独立解析器/外部工具复核，再导回新本体比较语义。
9. 无关编辑后复杂公理、共享属性、语言标签、数据类型及实例断言仍保留；重复导入不重复建模。
10. 通过发布页创建和审查新版本；导出该版本时不混入工作稿或本地未保存修改。

## 9. 本版已确定的设计决定

- 本体工作台菜单、页面、模型和持久化结构均可重做，以合理性和标准语义为准。
- 本体库与具体本体工作区分层；内部导航采用建模、数据、能力、检查、发布。
- 建模默认左对话右图；其他页面按任务提供足够空间，对话可在工作台左侧按需展开。
- 图编辑器与标准 `.rdf` / `.owl` 双向交换是首期主交付。
- 会话底层复用 Sudowork，用途和归属独立；本体会话不显示在普通会话列表。
- 不考虑旧本体数据兼容和迁移；不执行任何数据清理作为本轮方案工作的副作用。
- 新系统自身的保存、恢复、版本、并发与标准语义完整性必须做好。

完整 OWL 推理器、行业先验库、真实多人协作、全量实例知识图谱和额外外部连接器保持后续独立范围；完整工程包不替代标准文件交换。
