# 用户记忆跨会话现状及修复方案

## 1. 问题场景

以下内容在会话 A 中均能被 AI 记住，但新建会话 B 后无法回答：

```text
会话 A：请记住，我的测试代号是“蓝鲸-7429”。
会话 B：我的测试代号是什么？
```

```text
会话 A：请记住，以后查报价先查 A，再查 B。
会话 B：我要求的报价搜索顺序是什么？
```

这说明当前“记住”只在当前会话或当前 Workspace 生效，没有形成用户级跨会话记忆。

## 2. 已确认的实际行为

### 2.1 Scode 确实创建了长期记忆文件

实测在会话中输入“记住，我叫小黑”后，Scode 创建了：

```text
~/.scode/projects/<workspace-key>/memory/
├── MEMORY.md
└── user_name.md
```

其中：

- `user_name.md` 保存具体用户事实；
- `MEMORY.md` 是该 Workspace Memory 的索引。

因此，Scode 的 Memory 写入本身是成功的。

### 2.2 Scode Memory 按 Workspace 路径分区

`<workspace-key>` 由 Workspace 路径派生。例如：

```text
Workspace:
~/.nexus/scode-temp-1785941253952

Memory:
~/.scode/projects/-Users-...--nexus-scode-temp-1785941253952/memory/
```

从 Scode 视角看，这是 Workspace/项目级 Memory：不同代码目录拥有不同记忆。

### 2.3 Sudowork 默认每个会话创建不同 Workspace

默认本地 Scode 会话使用：

```text
会话 A → ~/.nexus/scode-temp-A
会话 B → ~/.nexus/scode-temp-B
```

相关代码：

```text
src/process/initAgent.ts
```

所以 Scode 实际产生：

```text
会话 A → ~/.scode/projects/<workspace-A>/memory
会话 B → ~/.scode/projects/<workspace-B>/memory
```

会话 B 不会读取会话 A 的 Memory。

### 2.4 当前 Workspace 的 AGENTS.md 也被更新

实测 Scode 还在当前 Workspace 根目录写入：

```text
<workspace>/AGENTS.md
```

其中增加：

```md
## Memory

- 用户名叫“小黑”；后续交流可称呼用户为“小黑”。
```

但该文件仍属于会话 A 的临时 Workspace，新会话 B 不会共享。

### 2.5 Sudowork 托管规则与 Scode 实际 Memory 并存

Sudowork 当前给 Scode 注入的规则要求长期记忆优先写入：

```text
<workspace>/.nexus/sudocode/AGENTS.md
```

相关代码：

```text
src/process/services/scode/ScodeInstallService.ts
```

实测又同时存在：

- `<workspace>/AGENTS.md`；
- `~/.scode/projects/<workspace-key>/memory/`；
- `<workspace>/.nexus/sudocode/AGENTS.md` 的托管规则。

当前有多套记忆落点，但没有明确的单一事实来源。

## 3. Memory 文件打不开的问题

### 3.1 AI 回复中展示的文件

Scode 回复类似：

```text
已更新：
.nexus/sudocode/AGENTS.md
长期记忆 user_name.md
长期记忆索引 MEMORY.md
```

### 3.2 文件真实位置

`user_name.md` 和 `MEMORY.md` 实际位于：

```text
~/.scode/projects/<workspace-key>/memory/
```

并不位于：

```text
<workspace>/user_name.md
<workspace>/MEMORY.md
```

### 3.3 Sudowork 的错误解析

Sudowork 将回复中的裸相对路径解析为当前 Workspace 普通文件：

```text
user_name.md → <workspace>/user_name.md
MEMORY.md    → <workspace>/MEMORY.md
```

日志中已出现：

```text
ENOENT: no such file or directory, stat '<workspace>/user_name.md'
ENOENT: no such file or directory, stat '<workspace>/MEMORY.md'
```

因此这是明确的 Sudowork 文件链接映射问题。

### 3.4 Memory 文件被错误纳入交付物归档

实测 Workspace 中还出现：

```text
<workspace>/.drafts/MEMORY.md
```

这是 Sudowork 文件意图跟踪/归档对 Memory 写入产生的副作用。Scode 内部 Memory 不应作为普通用户交付文件进入 `.drafts`。

## 4. 用户昵称不是通用 Memory

Sudowork 已有账号昵称专用链路：

```text
登录/修改昵称
→ ~/.nexus/user_nickname.txt
→ ~/.nexus/sudoclaw/workspace/USER.md
```

相关代码：

```text
src/renderer/context/AuthContext.tsx
src/process/bridge/authBridge.ts
src/process/services/sudoclaw/SudoclawInstallService.ts
```

这是用户资料字段的专门持久化，不能替代以下通用记忆：

- 测试代号；
- 输出偏好；
- 通用搜索顺序；
- 长期业务规则；
- 用户明确要求“以后都这样做”的工作流。

## 5. 根因

> Scode 提供的是按 Workspace 路径分区的 Memory；Sudowork 默认把每个 Conversation 绑定到不同临时 Workspace，却期待这些 Memory 表现为用户级跨会话记忆。

因此：

- Scode Memory 写入成功；
- Scode 按 Workspace 隔离的设计本身合理；
- Sudowork 没有为产品补充稳定的用户级 Memory 作用域；
- Sudowork 也没有正确映射 Scode 内部 Memory 文件路径。

主要问题位于 Sudowork 集成层，但若要原生复用 Scode Memory，Scode 可能需要提供独立于 Workspace 的 Memory scope/root 配置。

## 6. 修复目标

1. 用户明确要求长期记住的事实、偏好和流程可跨普通新会话使用。
2. 普通聊天内容和临时任务条件不自动跨会话。
3. 保留每会话独立 ACP Session 和临时 Workspace。
4. 不通过共享整个 Workspace 实现用户记忆。
5. Memory 只有一个明确的用户级事实来源。
6. Memory 文件链接可正确打开，或内部文件不作为普通交付文件展示。
7. 支持查看、更新、删除和清空用户记忆。
8. 不引入项目管理。

## 7. 推荐修复方向

### 7.1 优先确认 Scode 是否支持独立 Memory 作用域

优先调研 Scode 是否已经或可以提供：

```text
memory_scope = user
memory_root = <stable-user-memory-path>
memory_key = <stable-user-id>
```

理想行为：

```text
Scode cwd       = 当前会话独立 Workspace
Scode session   = 当前 Conversation 独立 ACP Session
Scode memory    = 稳定用户级 Memory
```

这样可以保留文件隔离，同时跨会话共享用户 Memory。

### 7.2 Scode 不支持时，由 Sudowork 管理用户级 Memory

如果 Scode 暂无独立 Memory scope，不建议直接依赖或改写其内部目录：

```text
~/.scode/projects/<workspace-key>/memory/
```

该路径属于 Scode 内部实现，随版本变化风险较高。

Sudowork 可以使用稳定的用户级目录作为单一事实来源，例如：

```text
~/.nexus/sudowork/sudocode/user-memory/
├── MEMORY.md
└── entries/
```

或者复用用户级：

```text
~/.nexus/sudowork/sudocode/AGENTS.md
```

中的受控 Memory 区块。

新 ACP Session 首条消息由 Sudowork 隐藏注入用户 Memory。

### 7.3 不建议通过稳定共享 Workspace 解决

不应让所有 Conversation 共同使用一个 Workspace，只为复用 Scode Memory。否则会引入：

- 临时文件互相污染；
- 文件重名；
- 删除会话影响其他会话；
- 不同任务互相看到无关附件；
- Workspace 生命周期失控。

正确解法是将 Memory scope 与 `cwd` 解耦。

## 8. 记忆写入规则

第一阶段只在用户明确表达长期意图时写入：

- “记住……”；
- “以后都……”；
- “以后默认……”；
- “下次也按这个流程……”；
- “长期使用……”；
- “忘记之前关于……的规则”。

普通陈述只保留在当前 Session。

### 8.1 适合用户级记忆

- 用户希望被如何称呼；
- 回复语言和格式偏好；
- 通用报价证据要求；
- 通用搜索顺序；
- 禁用的数据源；
- 长期业务规则。

### 8.2 不适合用户级记忆

- “这次只查北京”；
- 当前上传文件的临时说明；
- 某次报价结果；
- AI 未经用户确认的推断；
- 密码、Token、API Key 等敏感信息。

### 8.3 完整工作流与 Skill 的边界

- 简短事实和偏好：Memory；
- 多步骤、带工具、脚本或模板的稳定流程：Skill；
- 当前任务信息：Session。

## 9. 读取和注入规则

新建普通会话时：

```text
新 Conversation
+ 新 ACP Session
+ 新临时 Workspace
+ 用户级 Memory
```

用户级 Memory 只在新 ACP Session 首条消息中注入一次：

```text
[User Memory]
...

[User Request]
...
```

要求：

- 不显示在用户消息正文；
- 文件不存在或为空时跳过；
- 设置字符上限；
- 恢复原 ACP Session 时避免重复注入；
- 安全规则优先级高于用户 Memory；
- 支持按用户 ID 隔离，不能只按设备账户全局共享。

## 10. Memory 文件展示修复

### 10.1 推荐产品行为

Scode 内部 Memory 文件不应默认作为用户交付物展示。

用户只需要看到：

```text
已记住：用户名叫“小黑”。
```

不需要看到内部实现文件路径。

### 10.2 如果需要提供“查看记忆”

应通过专门的 Memory 查看入口或 IPC 返回结构化内容，而不是让 Renderer 猜测模型文本中的相对路径。

### 10.3 临时兼容

如果暂时仍展示 Scode 内部文件，必须传递真实绝对路径或专用 URI，并由主进程校验后打开。

禁止继续将：

```text
user_name.md
MEMORY.md
```

盲目解析为 Workspace 根目录文件。

### 10.4 排除归档

以下路径应从普通交付物跟踪和 `.drafts` 归档中排除：

```text
~/.scode/projects/*/memory/**
<workspace>/.nexus/sudocode/**
<workspace>/AGENTS.md（系统/记忆更新时）
```

仅用户明确要求导出记忆文件时，才作为交付物展示。

## 11. 基本管理能力

至少支持：

```text
记住：以后报价必须附来源
查看你记住了什么
忘记报价相关规则
清空通用记忆
```

要求：

- 更新同一事实而不是无限追加重复项；
- 删除和清空需要确认；
- 保存后返回实际写入成功状态；
- 写入失败不得回复“已记住”。

## 12. 建议实施阶段

### 阶段 1：调研和定责

1. 确认 Scode Memory 的正式接口和稳定性承诺；
2. 确认是否支持用户级 `memory_scope`、`memory_root` 或 `memory_key`；
3. 确认 Memory 路径键生成规则是否可配置；
4. 不基于未公开的 `~/.scode/projects` 内部格式直接开发长期依赖。

### 阶段 2：用户级 Memory 闭环

1. 确定用户级 Memory 单一事实来源；
2. 实现明确意图下的写入、更新和删除；
3. 新 ACP Session 注入；
4. 按用户 ID 隔离；
5. 增加长度与敏感信息限制；
6. 写入后读取验证，验证成功才回复“已记住”。

### 阶段 3：文件展示修复

1. 内部 Memory 文件不再作为普通交付物；
2. 修复相对路径错误解析；
3. 排除 `.drafts` 归档；
4. 增加专门的“查看记忆”界面或结构化消息。

## 13. 建议涉及文件

若由 Sudowork 管理用户级 Memory，可能涉及：

```text
src/process/services/scode/scodePaths.ts
src/process/services/scode/ScodeInstallService.ts
src/process/task/agentUtils.ts
src/process/task/AcpAgent.ts
src/process/task/acpWorkspaceTracking.ts
src/process/task/draftsCleanup.ts
src/process/bridge/fsBridge.ts
src/common/ipcBridge.ts
tests/unit/*
```

若 Scode 提供原生用户级 Memory 配置，则 Sudowork 主要负责传递稳定的用户 scope/key，并修复文件展示。

## 14. 验收场景

### 14.1 用户事实跨会话

```text
会话 A：请记住，我的测试代号是“蓝鲸-7429”。
会话 B：我的测试代号是什么？
```

预期：会话 B 正确回答。

### 14.2 通用流程跨会话

```text
会话 A：请记住，以后查报价先查 A，再查 B。
会话 B：我要求的报价搜索顺序是什么？
```

预期：会话 B 回答 A → B。

### 14.3 临时条件不跨会话

```text
会话 A：这次只查北京。
会话 B：查询地区是什么？
```

预期：不得把北京当作长期偏好。

### 14.4 忘记

```text
会话 A：忘记我的测试代号。
会话 B：我的测试代号是什么？
```

预期：无法再回答旧代号。

### 14.5 文件展示

保存记忆后点击相关文件或查看入口。

预期：

- 不出现 Workspace 根目录 `ENOENT`；
- 不生成错误的 `.drafts/MEMORY.md`；
- 内部 Memory 不被误报为普通交付文件。

### 14.6 会话隔离

会话 A 和 B 仍使用不同临时 Workspace。

预期：用户 Memory 共享，但临时文件和聊天历史不共享。

### 14.7 多用户隔离

同一设备登录用户 A 和用户 B。

预期：双方用户 Memory 不互相可见。

## 15. 非目标

本修复不处理：

- 项目管理；
- 自动继承其他会话全文；
- 自动总结所有历史会话；
- Skill 安装和启用；
- Remote/Moss 服务端 Memory；
- 多设备云同步。

这些能力应独立设计和实施。
