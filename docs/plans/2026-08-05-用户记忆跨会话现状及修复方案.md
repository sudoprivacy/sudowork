# 用户记忆与会话上下文跨会话现状及修复方案

## 1. 问题场景

以下内容在会话 A 中均能被 AI 记住，但新建会话 B 后无法回答：

```text
会话 A：请记住，我的测试代号是“蓝鲸-7429”。
会话 B：我的测试代号是什么？
```

```text
会话 A：请记住，以后查报价先查 A，再查 B。
会话 B：我要求的报价搜索顺序是什么？
```

普通聊天和任务上下文也存在同样问题：

```text
会话 A：这次报价只看北京，结果整理到“华北报价表”。
会话 B：继续处理刚才的报价，补上天津。
```

```text
会话 A：客户担心交付时间，我们讨论后决定先提供简版。
会话 B：客户之前主要担心什么？最终决定是什么？
```

这说明当前不仅“明确记住”的内容无法跨 Workspace 使用，普通聊天事实、临时任务条件、决策和未完成事项也缺少跨会话召回能力。

## 2. 已确认的实际行为

### 2.1 Scode 确实创建了长期记忆文件

实测在会话中输入“记住，我叫小黑”后，Scode 创建了：

```text
~/.scode/projects/<workspace-key>/memory/
├── MEMORY.md
└── user_name.md
```

其中：

- `user_name.md` 保存具体用户事实；
- `MEMORY.md` 是该 Workspace Memory 的索引。

因此，Scode 的 Memory 写入本身是成功的。

### 2.2 Scode Memory 按 Workspace 路径分区

`<workspace-key>` 由 Workspace 路径派生。例如：

```text
Workspace:
~/.nexus/scode-temp-1785941253952

Memory:
~/.scode/projects/-Users-...--nexus-scode-temp-1785941253952/memory/
```

从 Scode 视角看，这是 Workspace/项目级 Memory：不同代码目录拥有不同记忆。

### 2.3 Sudowork 默认每个会话创建不同 Workspace

默认本地 Scode 会话使用：

```text
会话 A → ~/.nexus/scode-temp-A
会话 B → ~/.nexus/scode-temp-B
```

相关代码：

```text
src/process/initAgent.ts
```

所以 Scode 实际产生：

```text
会话 A → ~/.scode/projects/<workspace-A>/memory
会话 B → ~/.scode/projects/<workspace-B>/memory
```

会话 B 不会读取会话 A 的 Memory。

### 2.4 当前 Workspace 的 AGENTS.md 也被更新

实测 Scode 还在当前 Workspace 根目录写入：

```text
<workspace>/AGENTS.md
```

其中增加：

```md
## Memory

- 用户名叫“小黑”；后续交流可称呼用户为“小黑”。
```

但该文件仍属于会话 A 的临时 Workspace，新会话 B 不会共享。

### 2.5 Sudowork 托管规则与 Scode 实际 Memory 并存

Sudowork 当前给 Scode 注入的规则要求长期记忆优先写入：

```text
<workspace>/.nexus/sudocode/AGENTS.md
```

相关代码：

```text
src/process/services/scode/ScodeInstallService.ts
```

实测又同时存在：

- `<workspace>/AGENTS.md`；
- `~/.scode/projects/<workspace-key>/memory/`；
- `<workspace>/.nexus/sudocode/AGENTS.md` 的托管规则。

当前有多套记忆落点，但没有明确的单一事实来源。

### 2.6 Scode 已支持独立 Memory 目录

本机嵌入版 `scode 0.1.16` 已验证支持：

```text
SUDOCODE_MEMORY_DIR=<stable-memory-path>
```

在两个不同 Workspace 下设置相同的 `SUDOCODE_MEMORY_DIR`，`scode system-prompt` 均解析到同一个 Memory 目录。因此，Scode Memory 已可与 `cwd` 解耦，不需要依赖或改写：

```text
~/.scode/projects/<workspace-key>/memory/
```

当前 Sudowork 只注入了 `SUDO_CODE_CONFIG_HOME` 等环境变量，尚未注入 `SUDOCODE_MEMORY_DIR`。该变量目前由实际二进制行为验证，仍需通过真实二进制集成测试锁定兼容合同，并向 Scode 上游确认稳定性承诺。

## 3. Memory 文件打不开的问题

### 3.1 AI 回复中展示的文件

Scode 回复类似：

```text
已更新：
.nexus/sudocode/AGENTS.md
长期记忆 user_name.md
长期记忆索引 MEMORY.md
```

### 3.2 文件真实位置

`user_name.md` 和 `MEMORY.md` 实际位于：

```text
~/.scode/projects/<workspace-key>/memory/
```

并不位于：

```text
<workspace>/user_name.md
<workspace>/MEMORY.md
```

### 3.3 Sudowork 的错误解析

Sudowork 将回复中的裸相对路径解析为当前 Workspace 普通文件：

```text
user_name.md → <workspace>/user_name.md
MEMORY.md    → <workspace>/MEMORY.md
```

日志中已出现：

```text
ENOENT: no such file or directory, stat '<workspace>/user_name.md'
ENOENT: no such file or directory, stat '<workspace>/MEMORY.md'
```

因此这是明确的 Sudowork 文件链接映射问题。

### 3.4 Memory 文件被错误纳入交付物归档

实测 Workspace 中还出现：

```text
<workspace>/.drafts/MEMORY.md
```

这是 Sudowork 文件意图跟踪/归档对 Memory 写入产生的副作用。Scode 内部 Memory 不应作为普通用户交付文件进入 `.drafts`。

## 4. 用户昵称不是通用 Memory

Sudowork 已有账号昵称专用链路：

```text
登录/修改昵称
→ ~/.nexus/user_nickname.txt
→ ~/.nexus/sudoclaw/workspace/USER.md
```

相关代码：

```text
src/renderer/context/AuthContext.tsx
src/process/bridge/authBridge.ts
src/process/services/sudoclaw/SudoclawInstallService.ts
```

这是用户资料字段的专门持久化，不能替代以下通用记忆：

- 测试代号；
- 输出偏好；
- 通用搜索顺序；
- 长期业务规则；
- 用户明确要求“以后都这样做”的工作流。

## 5. 根因

> Sudowork 没有把 Scode 已支持的 Memory 目录与会话 Workspace 解耦，也没有为普通聊天和任务上下文提供跨会话检索链路。

因此存在两个独立缺口：

1. **用户记忆缺口**：Sudowork 未向嵌入版 Scode 注入稳定、按用户隔离的 `SUDOCODE_MEMORY_DIR`，导致 Memory 默认随 Workspace 分区。
2. **会话上下文缺口**：普通聊天事实、任务条件、决策和未完成事项只存在于原会话历史，没有在后续会话中按需召回。

另外，当前托管规则要求 Scode 优先写入当前 Workspace 的 `.nexus/sudocode/AGENTS.md`，与稳定用户级 Memory 目标冲突；文件操作展示又会把内部 Memory 文件误当作 Workspace 交付物。

主要问题位于 Sudowork 集成层。Scode 原生 Memory 负责用户级记忆；Sudowork 负责用户身份映射、历史会话检索和产品展示。

## 6. 修复目标

1. 用户明确要求长期记住的事实、偏好和流程可跨普通新会话使用。
2. 普通聊天事实、临时任务条件、决策和未完成事项可自动跨会话召回。
3. 召回按当前问题相关性进行，不把全部历史会话无差别注入上下文。
4. 保留每会话独立 ACP Session 和临时 Workspace。
5. 不通过共享整个 Workspace 实现跨会话能力。
6. 用户级 Memory、原始会话历史和派生检索数据职责清晰，不形成互相冲突的事实副本。
7. 内部 Memory 文件不作为普通交付文件展示或归档。
8. 支持查看、更新、删除和清空用户记忆；支持关闭或清理历史召回数据。
9. 按用户 ID 隔离，同一设备上的不同账号不能互相召回。
10. 不引入项目管理。

### 6.1 可达到的使用场景

```text
会话 A：这次只查北京的报价，客户比较在意交付时间，先整理简版。
会话 B：继续上次的报价任务，再补上天津。
```

预期：会话 B 自动召回“北京报价、客户关注交付时间、先做简版”，并在此基础上补查天津，不要求用户重新描述背景。

之后开启无关报价任务时，系统不会把“只查北京”当作永久默认条件；只有相关历史会被召回。用户也可以说“这次不要参考历史”，让本轮从空白上下文开始。

## 7. 推荐修复方向

### 7.1 使用 Scode 原生用户级 Memory

为每个用户派生稳定目录，并在启动嵌入版 Scode 时注入：

```text
SUDOCODE_MEMORY_DIR=~/.nexus/sudowork/sudocode/user-memory/<user-key>
```

目标行为：

```text
Scode cwd       = 当前会话独立 Workspace
Scode session   = 当前 Conversation 独立 ACP Session
Scode memory    = 当前登录用户的稳定 Memory 目录
```

要求：

- `<user-key>` 由稳定用户 ID 安全派生，不使用昵称；
- 登录用户和游客使用不同作用域；
- 切换账号时切换 Memory 目录，不删除原账号数据；
- 启动前确保目录存在；
- 不直接读写 `~/.scode/projects` 内部目录；
- 增加真实 Scode 二进制合同测试，验证不同 cwd 使用同一目录；
- 若未来 Scode 不再支持该变量，测试必须显式失败，不能静默退回 Workspace Memory。

当前 `ScodeInstallService.ts` 中“优先写 Workspace `.nexus/sudocode/AGENTS.md`”的规则应删除或改写，避免与 Scode 原生 Memory 冲突。

### 7.2 使用现有会话历史实现自动相关召回

`SUDOCODE_MEMORY_DIR` 解决用户级 Memory，但不能替代普通聊天和任务上下文。Sudowork 应继续以现有会话消息存储为原始事实来源，在每轮用户请求时检索当前用户的相关历史。

推荐数据职责：

```text
用户事实、偏好、长期规则
→ Scode Memory（用户级，可更新/忘记）

普通聊天、任务条件、决策、未完成事项
→ 原始会话历史（事实来源）
→ 可重建的摘要/检索索引（仅用于召回）
```

检索结果以隐藏上下文注入：

```text
[Relevant Prior Context]
- 来源会话、时间、相关事实或任务状态

[User Request]
...
```

要求：

- 每轮按当前请求相关性检索，而不只在新会话首条消息注入；
- 优先召回明确事实、任务约束、决策、未完成事项和最近相关讨论；
- 保留来源会话 ID 和时间，避免把摘要当作无来源事实；
- 原始消息更新或删除后，派生摘要/索引可重建或同步删除；
- 设置检索条数和字符上限，不注入全部历史全文；
- 当前会话已包含的内容不重复注入；
- 用户要求忽略历史时，本轮跳过召回。

第一阶段可先复用现有本地会话存储和简单文本检索；只有数据量或召回质量实际不足时，再增加向量索引，不预先引入新的检索依赖。

### 7.3 不建议通过稳定共享 Workspace 解决

不应让所有 Conversation 共同使用一个 Workspace，只为复用 Memory。否则会引入：

- 临时文件互相污染；
- 文件重名；
- 删除会话影响其他会话；
- 不同任务互相看到无关附件；
- Workspace 生命周期失控。

正确解法是分别将用户 Memory 和历史召回与 `cwd` 解耦。

## 8. 自动保存与召回规则

默认允许跨会话使用普通聊天和任务上下文，但不同内容进入不同存储层，避免把一次性条件错误提升为永久偏好。

### 8.1 用户级 Memory

适合写入 Scode Memory：

- 用户明确要求“记住”“以后默认”“下次也按这个流程”的内容；
- 用户希望被如何称呼；
- 稳定的回复语言和格式偏好；
- 通用报价证据要求、搜索顺序和禁用数据源；
- 多次出现且上下文明确的稳定工作习惯；
- 用户要求更新或忘记的既有记忆。

自动推断的长期偏好必须保留不确定性；不能把单次行为直接升级为永久规则。

### 8.2 历史会话上下文

以下内容不必写成永久用户 Memory，但必须保留在会话历史并可自动召回：

- “这次只查北京”等任务条件；
- 当前上传文件的说明；
- 某次报价结果和证据；
- 已作出的选择及原因；
- 未完成事项、下一步和阻塞项；
- 普通聊天中出现的人、事、时间和业务背景。

临时不等于不可跨会话。它只表示该信息不能被当作永久默认值；当后续请求与原任务相关时，仍应召回。

### 8.3 禁止自动保存或注入

- 密码、Token、API Key、私钥和验证码；
- AI 未经依据生成的推断；
- 已被用户删除或要求忽略的内容；
- 其他账号的 Memory 或会话历史。

### 8.4 Memory、History 与 Skill 的边界

- 稳定事实、偏好和长期规则：Memory；
- 普通聊天、任务条件、决策和进度：History + 相关召回；
- 多步骤、带工具、脚本或模板的稳定流程：Skill；
- 当前 ACP 对话上下文：Session。

同一信息可以从 History 提炼到 Memory，但 Memory 是可更新的用户级结论，History 仍保留原始来源。

## 9. 读取和注入规则

新建普通会话时：

```text
新 Conversation
+ 新 ACP Session
+ 新临时 Workspace
+ Scode 自动加载当前用户 Memory
+ Sudowork 按当前请求检索相关历史
```

用户级 Memory 通过 `SUDOCODE_MEMORY_DIR` 由 Scode 原生加载，Sudowork 不再复制完整 Memory 到首条用户消息。

历史召回由 Sudowork 在每轮请求前按需注入：

```text
[Relevant Prior Context]
...

[User Request]
...
```

要求：

- 隐藏上下文不显示在用户消息正文；
- 没有相关结果时跳过；
- 设置条数和字符上限；
- 标注来源会话和时间；
- 恢复原 ACP Session 或当前上下文已包含时避免重复注入；
- 安全规则和当前用户明确指令优先于历史内容；
- 当前代码和文件状态优先于历史摘要；
- 按用户 ID 隔离，不能只按设备全局共享；
- 用户可要求本轮忽略历史或关闭自动召回。

## 10. Memory 文件展示修复

### 10.1 推荐产品行为

Scode 内部 Memory 文件和 Sudowork 的历史检索索引不应默认作为用户交付物展示。

用户只需要看到：

```text
已记住：用户名叫“小黑”。
```

不需要看到内部实现文件路径。

### 10.2 如果需要提供“查看记忆”

应通过专门的 Memory 查看入口或 IPC 返回结构化内容，而不是让 Renderer 猜测模型文本中的相对路径。

### 10.3 临时兼容

如果暂时仍展示 Scode 内部文件，必须传递真实绝对路径或专用 URI，并由主进程校验后打开。

禁止继续将：

```text
user_name.md
MEMORY.md
```

盲目解析为 Workspace 根目录文件。

### 10.4 排除归档

以下路径应从普通文件操作消息、交付物跟踪和 `.drafts` 归档中排除：

```text
$SUDOCODE_MEMORY_DIR/**
~/.scode/projects/*/memory/**（旧版本兼容）
<workspace>/.nexus/sudocode/**
<workspace>/AGENTS.md（系统更新时）
<历史摘要或检索索引目录>/**
```

`AcpAgent` 在展示和跟踪文件操作前必须先识别真实绝对路径；禁止把内部 Memory 的裸文件名按 Workspace 根目录解析。

仅用户明确要求导出记忆或历史时，才生成独立导出文件并作为交付物展示。

## 11. 基本管理能力

至少支持：

```text
记住：以后报价必须附来源
查看你记住了什么
忘记报价相关规则
清空通用记忆
继续上个会话的报价任务
客户之前主要担心什么
这次不要参考历史会话
```

要求：

- 更新同一用户事实而不是无限追加重复项；
- 能区分“永久偏好”和“某次任务条件”；
- 删除和清空用户 Memory 需要确认；
- 删除会话时同步删除或重建其派生检索数据；
- 保存后返回实际写入成功状态；
- 写入失败不得回复“已记住”；
- 召回结果应可追溯到来源会话，不能伪装成当前用户刚刚提供的信息。

## 12. 分步实施任务

每个任务应独立提交、独立验证。前一个任务验收通过后再进入下一个，避免同时改动 Memory 存储、历史召回和 UI。

### 里程碑 A：统一用户 Memory

完成任务 1～5 后，显式保存的用户事实、偏好和规则可以跨新会话使用；不同会话仍保持独立 Workspace。

#### 任务 1：锁定 Scode Memory 环境变量合同

- [x] 使用当前打包版本的真实 `scode` 二进制验证 `SUDOCODE_MEMORY_DIR`；
- [x] 验证两个不同 cwd 设置同一目录后，system prompt 指向同一个 Memory；
- [x] 增加真实二进制集成测试，环境变量失效时显式失败；
- [ ] 向 Scode 上游确认稳定性承诺，不阻塞本地已验证版本的实现。

验收：测试能够证明 Memory 路径由 `SUDOCODE_MEMORY_DIR` 决定，而不是由 Workspace 路径决定。

#### 任务 2：定义用户 Memory 路径和身份作用域

- [x] 在 `scodePaths.ts` 定义用户 Memory 根目录；
- [x] 使用稳定用户 ID 安全派生 `<user-key>`，不使用昵称或未经处理的原始 ID；
- [x] 明确游客使用独立的本机 guest scope；
- [x] 启动 Scode 前创建对应目录；
- [x] 切换账号时切换目录，不删除原账号数据。

目标目录：

```text
~/.nexus/sudowork/sudocode/user-memory/<user-key>/
```

验收：用户 A、用户 B 和游客得到三个不同的稳定目录；同一用户重复登录得到同一目录。

#### 任务 3：启动 Scode 时注入用户 Memory 目录

依赖：任务 1、2。

- [x] 将当前用户的 Memory 路径传入 Scode 启动环境；
- [x] 保留现有 `SUDO_CODE_CONFIG_HOME` 和其他 Scode 环境变量；
- [x] 恢复会话、重连和模型切换后仍使用同一用户目录；
- [x] 账号切换后不复用旧账号仍在运行的 Scode 进程。

验收：

```text
会话 C Workspace ≠ 会话 D Workspace
会话 C Memory = 会话 D Memory
用户 A Memory ≠ 用户 B Memory
```

#### 任务 4：取消 Workspace Memory 双写

依赖：任务 3。

- [x] 修改 `ScodeInstallService.ts` 的托管规则；
- [x] 删除“长期记忆优先写入 Workspace `.nexus/sudocode/AGENTS.md`”的要求；
- [x] 明确用户记忆只写入 Scode 提供的 persistent Memory 目录；
- [x] Workspace `AGENTS.md` 只承载项目/运行规则，不承载用户记忆。

## 14. 验收场景

### 14.1 用户事实跨会话

```text
会话 A：请记住，我的测试代号是“蓝鲸-7429”。
会话 B：我的测试代号是什么？
```

预期：会话 B 正确回答。

### 14.2 通用流程跨会话

```text
会话 A：请记住，以后查报价先查 A，再查 B。
会话 B：我要求的报价搜索顺序是什么？
```

预期：会话 B 回答 A → B。

### 14.3 临时条件按相关任务跨会话

```text
会话 A：这次只查北京，结果整理到“华北报价表”。
会话 B：继续刚才的报价任务，查询地区是什么？
```

预期：召回北京和“华北报价表”，但不得把北京写成所有未来报价的长期默认地区。

### 14.4 普通聊天事实跨会话

```text
会话 A：客户担心交付时间，我们讨论后决定先提供简版。
会话 B：客户之前主要担心什么？最终决定是什么？
```

预期：回答“交付时间”和“先提供简版”，并可追溯到会话 A。

### 14.5 忘记

```text
会话 A：忘记我的测试代号。
会话 B：我的测试代号是什么？
```

预期：无法再回答旧代号。

### 14.6 文件展示

保存记忆后点击相关文件或查看入口。

预期：

- 不出现 Workspace 根目录 `ENOENT`；
- 不生成错误的 `.drafts/MEMORY.md`；
- 内部 Memory 不被误报为普通交付文件。

### 14.7 会话隔离与相关召回

会话 A 和 B 仍使用不同临时 Workspace，并拥有独立 ACP Session。

预期：

- 用户 Memory 共享；
- 临时文件和会话全文不直接合并；
- 只有与当前请求相关的历史片段被隐藏召回；
- 无关会话内容不得进入回答。

### 14.8 忽略历史

```text
会话 B：这次不要参考任何历史会话，重新分析。
```

预期：本轮不注入历史召回结果，但不删除已有 Memory 或历史记录。

### 14.9 多用户隔离

同一设备登录用户 A 和用户 B。

预期：双方的用户 Memory、原始会话历史和派生检索数据均不互相可见或召回。

## 15. 非目标

本修复不处理：

- 项目管理；
- 将其他会话全文无差别注入每个新会话；
- Skill 安装和启用；
- Remote/Moss 服务端 Memory；
- 多设备云同步。

本方案包含本地历史的自动摘要或索引与相关召回，但不等于自动继承全部历史全文。远端和多设备能力应独立设计。
