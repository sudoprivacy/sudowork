## 1. 产品结论

让目录展示与安装状态分开：用户先看到当前组织允许其看到的目录，在 Sudowork 点击使用或下载时，才把选中的资源下载到本机。“我的”以本机实际成功下载为准，不以 Moss 是否安装为准。

| 入口 | 展示内容 | 是否要求 Moss 预先安装 | 是否要求本机已下载 |
| --- | --- | --- | --- |
| 智能体库 / 技能库 | 当前 Moss 提供的公共目录，遵守当前账号可见权限 | 否 | 否 |
| 专属智能体 / 专属技能 | 当前组织在 Moss 发布或管理、当前账号可见的专属目录 | 否 | 否 |
| 我的智能体 / 我的技能 | 当前账号在这台设备上已成功下载的资源，以及原有本地创建、导入资源 | 否；服务端安装不能直接成为“我的” | 是；本地创建、导入也属于本机资源 |

“我的”建议用一个列表加来源筛选：全部、来自智能体库/技能库、来自组织、我创建或导入。技能现有内置资源保留为单独来源，不计入下载数量。无需在“我的”内部再出现两个看起来像商店入口的“库 / 专属”分区。

卡片行为：未下载显示“下载”“使用”；已下载显示“已下载”“使用”；有新版本显示“可更新”。“我的”提供本机启用/停用、更新、移除。来源相同的资源在目录和“我的”同时出现是正常的：一个用于发现，一个用于管理本机下载。

### 可见与可用的边界

- “与 Moss 一致”按同一服务、同一组织、同一账号和相同筛选条件比较，不把管理员可见范围复制给普通成员。
- Moss 允许管理员或创建者查看待审核、驳回、停用条目。Sudowork 对同一身份保留相同可见条目和状态，但下载、使用按钮受可用权限约束，不把这些条目变成普通成员可用资源。
- 目录可见不等于可以使用。Moss 返回明确的可用状态及原因；列表、详情、下载和执行沿用相同权限规则。
- 已下载不等于支持本地执行。依赖工作流、知识库、企业应用或云端 MCP 的智能体仍可下载其可分发资源并出现在“我的”，标记“仅支持云端执行”。

## 2. 当前代码为什么不符合目标

| 现状 | 影响 | 改造要求 |
| --- | --- | --- |
| Sudowork 企业模式智能体库从账户目录中的 `assistants/hub` 读取；专属页读 `assistants/tenant` | 没同步到本地就看不到，目录被安装状态限制 | 目录改读 Moss 的目录接口 |
| 技能库列表、分类、详情读取全局 `SKILLS_ROOT_DIR`，而“我的”和同步使用账号目录 | 2026-09-28 实际看到 7 个全局旧技能；2026-09-29 复核代码仍未修复 | 目录改读 Moss；所有本地状态只读当前账号根目录 |
| 专属技能直接从本机 installedList 过滤；专属智能体卡片写死已安装 | 可见、下载和可用状态混淆 | 目录和本地下载状态分别取数后按稳定 ID 关联 |

| 现有 `prepareMossResources` 只在组织账号的本地执行分支调用，且只查询 installed | 不能直接覆盖云端目录中的首次使用 | 提取共享下载逻辑，云端和本地执行分别进行能力校验 |
| 技能同步完成只刷新“我的”；专属技能分类未参与实际过滤 | 列表和分类结果可能不更新 | 明确目录刷新、下载变更两类事件，统一筛选 |

## 3. 展示与接口方案

优先复用 Moss 管理页面已经使用的接口，不再让 Sudowork 直连另一套 Hub，也不另建一套目录数据库。

| Sudowork 入口 | Moss 已有接口 |
| --- | --- |
| 智能体库 | `GET /api/v1/agent-hub/assistants/cursor`，对应 categories、详情接口 |
| 专属智能体 | `GET /api/v1/agents/tenant`，对应详情、rules 接口 |
| 技能库 | `GET /api/v1/skill-hub/skills/cursor`，对应 categories、详情接口 |
| 专属技能 | `GET /api/v1/skills/tenant`，对应详情接口 |
| 首次使用准备 | `POST /api/v1/client/catalog/install` |
| 下载资源 | 已鉴权的 `/api/v1/{agents,skills}/installed/{id}/download` 或 tenant 下载接口 |
| 我的资源 | Sudowork 当前账号的本机安装记录和资源文件，不用 Moss installed 接口生成列表 |

Moss 负责统一目录可见与使用权限判定，复用到上述列表/详情与 install 接口，并补充客户端需要的状态字段。公共目录现有代理主要负责转发，安装接口又有发布状态与权限检查，改造时必须消除“列表显示可用、点使用才发现规则不同”的不一致。Moss 管理页面继续使用同一服务逻辑。

专属目录保留管理身份可见条目，返回审核状态、启用状态、是否可下载/可使用及原因；不以 `status=approved` 的单一查询替代管理页面的完整可见规则。普通成员只能看到自己的权限范围。

Sudowork 主进程负责鉴权请求和响应校验，经 IPC 提供给渲染进程。统一客户端资源描述至少包括：资源种类、来源、稳定 ID、名称、分类、版本、可用状态、执行能力和依赖。组织身份从登录会话取得，不能由任意 tenant_id 参数决定。

最新质量配置中的 `product_improvement.tenant_id` 是质量上报使用的组织编码，不能代替资源鉴权所用的 orgId 或本机 accountScope。目录请求继续使用当前 Moss 登录 token；质量上报地址和 API Key 不能用于目录请求。

公共目录保留服务端分页、搜索、分类；专属目录可沿用现有列表返回后在本机过滤，但分类与搜索必须针对同一份目录数据。加载失败显示错误和重试，不能伪装成“目录为空”。目录缓存按服务器、组织、用户隔离，只缓存元数据，不触发包下载。

## 4. 下载与使用流程

### 首次点击“使用”

1. 固定本次操作的服务器、组织、用户、资源种类、来源和 ID；重新确认当前可见与可用状态。
2. 调用 Moss `client/catalog/install`。公共资源由 Moss 从可信目录解析并按当前用户准备资源及依赖；组织专属资源复用现有发布包并校验依赖。用户无需进入 Moss 手工安装。
3. Moss 返回本次解析的资源与依赖清单，包含稳定 ID、来源、确定的版本或内容摘要、鉴权下载引用和云端运行引用。现有接口仅返回名称等字段，需要扩展；不能靠名称猜资源，也不能下载过程中静默换到新版本。
4. Sudowork 下载选中资源及必要技能依赖到当前账号临时目录，校验摘要、包路径和必要文件。资源包只能包含可分发内容，Moss 运行凭据及服务端连接配置不进入本机包。
5. 资源及必需依赖全部完成后，原子提交本机安装记录。资源出现在“我的智能体”，实际下载的依赖出现在“我的技能”并标记用途。并发点击同一资源复用同一准备任务。
6. 进入对话。保持现有云端会话在首条消息时创建的机制；发送前再次检查权限与云端资源状态，使用稳定运行引用携带智能体和技能选择，不用本地绝对路径或摘要目录名调用云端资源。

后续使用复用本机完整下载，云端侧仍检查当前权限及包是否可用。准备接口应幂等，命中同一版本时不重复安装、不改变组织共享资源配置。

“下载”执行上述准备和本机下载，但不创建对话。公共包在此过程中可能被 Moss 缓存或记录为该用户可运行资源；这不代表另一台设备也已经下载，更不能让其他成员的“我的”增加条目。

独立技能也走同一流程；在聊天中勾选尚未下载的技能时先完成准备，再发送消息。智能体依赖不能只更新 UI 列表，必须落实到首次发送、续聊和新增技能时的运行参数。

接口契约建议在原有 install 返回字段上增量增加 `preparationId`、`resources`。每项包含 `kind/source/id/version/digest/downloadRef/runtimeRef/dependencies`；准备记录绑定当前组织、用户和不可变资源图，不能作为免鉴权凭据。下载引用必须指向本次确定的包，不能每次临时打包成不同字节却复用同一摘要；可以由服务端保存准备阶段的归档。客户端在本机安装记录及待建对话中保存准备引用，首次发送交给 Moss 校验并绑定版本。若准备引用过期，重新准备并比较版本；发生变化时提示更新，不能静默运行另一版本。该契约是拟新增能力，现有接口尚未提供。

### 必须拆开的状态

- 目录可见：来自 Moss 的目录与权限。
- 本机安装：未下载、下载中、已下载、失败；“我的”只展示成功记录及保留的本机资源。
- 云端准备：未准备、准备中、可运行、失败；运行时校验，不冒充本机下载状态。
- 可用权限、可用版本、本机启用状态另行记录，不用一个 `installed` 或 `enabled` 混代。

现有 `prepareMossResources` 把下载与本地执行限制写在一起。应拆成“包下载和完整性校验”与“本地执行能力校验”：云端专用智能体不能因包含 workflow/MCP/知识库依赖就在下载步骤被拒绝。本地执行仍保留当前限制。

### 失败与重试

必需依赖失败、摘要不匹配或本地写入失败时，整组本机安装不提交，不启动执行，不显示“已下载”。此前已存在的有效安装保留。临时文件清理；已经完成的不可变包可以留作内部缓存，但不作为“我的”新条目。

Moss 已准备成功、但本机下载失败时，允许服务端缓存保留；重试复用它。不要为了回滚本机失败而卸载组织共享资源。反过来，本机已完整下载但后来云端不可用时，“我的”仍保留已下载状态，使用按钮提示云端准备失败并可重试。

## 5. 本机存储、更新和兼容

- 复用已有 `accountScope = 服务器 + 组织 + 用户` 隔离，安装身份使用账号范围、资源种类、来源、稳定 ID；摘要只表示版本。不同组织或同名资源不能互相覆盖。
- 使用持久化本机安装清单作为“我的”的依据；清单关联完整包目录和依赖引用。现有元数据可复用，不要求新增数据库服务。单一资源的多个历史快照只显示一个安装条目。
- 复用摘要校验、暂存后 rename 和 `.moss-ready` 思路；云端和本地共用下载校验。读取旧本地会话快照时继续兼容已有 hub 路径，新来源不能破坏旧会话根目录校验。
- 本机启用/停用只控制新对话选择，不改变 Moss 组织资源的 enabled。移除只删除当前设备的安装关系，不删除 Moss 的公共包、专属资源或其他用户的数据。
- 被其他已安装智能体依赖的技能不能直接移除，需提示依赖；移除父智能体后，仍被其他安装或历史会话引用的快照保留。无引用缓存才允许后续回收。
- 登录、进入商店、刷新和切换执行模式均不全量下载。可刷新目录、权限和已有下载的版本信息；新版本显示“可更新”，用户更新后供新对话使用。
- 保留最新登录/恢复流程的 `fetchAndCacheCredentials`、`bootstrapClientReporting`、组织系统配置与凭据缓存，改造仅移除或替换资源全量同步触发点。目录加载和资源准备不得新增对质量服务初始化、上报成功或用户开启产品改进计划的依赖。
- 新会话绑定准备清单对应版本；旧会话继续沿用本地摘要快照和 Moss 既有会话快照机制。更新不能替换正在使用的版本；续聊仍重新检查访问权限。
- 会话执行位置沿用已持久化的 `executionTarget` 及现有判定规则，不根据是否下载、库/专属来源或首页当前模式改写。客户端资源安装属于本机动作，但随后的云端对话仍是 remote，不能因此重复上报为本地会话质量事件；不在本方案中新建一套质量上报逻辑。
- 本期不新增组织资源离线执行授权。断网可查看“我的”和同账号缓存目录，标明缓存；新下载与云端使用需要联网。本地执行也保留现有组织授权校验规则。
- 账号切换时取消或丢弃前一身份的请求结果；同一用户刷新 token 不应被误判为换账号。目录请求和下载任务都检查账号范围，不能把上一个组织的结果写入当前清单。

### 现有数据迁移

保留当前账号中此前自动同步、手动安装和导入的完整包，将能够确认身份的包登记为已有本机安装，不清空用户数据。旧版本没有可靠的“用户主动下载”标志，不能事后把它们认定为无用缓存。新账号或新设备从零下载开始；现有用户移除后，自动同步不能把它装回来。

对来源误写为 hub 的旧 tenant 包，结合原账号目录和服务端稳定 ID 修正；证据不足时保留为待确认本机资源并禁止自动上传/执行，不猜归属。全局 `~/.nexus/skills/hub` 不自动导入当前组织，避免继续混用账号。历史会话绑定的资源不因本次迁移而删除。

## 6. 两个仓库的实施范围

| 仓库 | 主要改动 | 完成标准 |
| --- | --- | --- |
| Moss | 统一目录与安装权限；补充可用状态；扩展 client/catalog/install 的确定版本及依赖清单；稳定下载/运行引用；幂等与并发处理 | 无需组织管理员预安装即可浏览及按需使用，所有接口遵守同一身份权限 |
| Sudowork | agent/skill IPC 目录改接 Moss；独立目录与本机安装状态；新增按需下载编排；取消全量自动安装；修复来源、账号目录和刷新问题；接通云端首发/续聊 | 浏览不下载，使用才准备，“我的”只反映当前设备实际资源 |

顺序建议：先确定 Moss 返回契约和对应测试，再实现 Sudowork 下载/状态层，最后接两个页面和会话入口并进行双端验收。两个仓库可分别形成 PR；部署时先 Moss 后 Sudowork。客户端检测服务端是否支持所需契约，旧服务端缺少能力时显示升级提示，不回退到自动全量同步。用字段或能力版本做兼容，不依赖对 JSON 字段的猜测。

## 7. 验收清单

| 场景 | 必须通过的结果 |
| --- | --- |
| 新设备、组织无公共安装记录 | 同一账号在 Moss 可见的库和专属条目在 Sudowork 可见；“我的”无新下载条目 |
| 浏览、搜索、翻页、切换分类 | 不下载 ZIP、不创建安装记录；结果及状态与同身份 Moss 对齐 |
| 智能体首次使用 | 资源与必需技能下载成功进入各自“我的”；Moss 无需人工预安装；真实云端回复体现智能体规则 |
| 独立技能首次使用 | 下载后可选择，首次发送和续聊中实际调用该技能，不只是看到卡片 |
| 下载但不聊天 | 本机增加条目；不创建 Moss 对话；重启后保持 |
| 依赖或下载失败、取消、并发点击 | 不出现半安装智能体、不重复记录、不启动缺依赖的对话；重试成功 |
| 两组织、同组织两用户、同用户两设备、同名不同 ID | 目录按权限隔离；“我的”按账号和设备隔离；资源及版本不串用 |
| 管理员/创建者与普通成员 | 可见状态与 Moss 一致；待审核/停用资源不可使用；手工调用详情/下载/执行也不能绕过 |
| 云端专用智能体 | 可下载、显示能力标记、可云端执行；切换本地执行时明确说明不支持 |
| 更新、停用、撤权、移除和旧会话 | 更新不替换会话快照；撤权不能通过旧缓存继续执行；本机移除不删除服务端数据，不被刷新自动重装 |
| 迁移既有测试数据 | 已有账号、文件、下载、历史对话保留；全局 7 个旧技能不会混入当前组织目录 |
| 登录、重启恢复、刷新 token 和切换组织 | 配置及凭据初始化继续工作；目录和下载始终使用当前组织身份，不把质量配置的组织编码当成 orgId |
| 下载后云端使用、切换首页模式、恢复旧任务 | 下载记录正确；会话实际执行位置不变，云端任务不被客户端误记为本地质量事件 |
| 质量服务关闭、未就绪或上报失败 | 目录浏览、下载和云端使用不依赖质量服务成功；保留现有 SQLite 测试数据，不为验证商店而迁移 PostgreSQL |
| 完整云端对话回归 | 普通/智能体/技能对话、续聊、上传文件、生成交付物、下载文件全部验证；临时产物继续进入草稿箱，内容格式保持有效 |

实施后应运行两仓库适用的单元、集成、类型与构建检查，以及实际双端回归。Sudowork 按项目要求执行文件级 lint、`bunx tsc --noEmit`、提交前 `bun run test`；Moss 运行其对应目录/安装/权限/运行与打包检查。只有真实模型执行和文件回归也通过，才可声称整条使用链路完成。

若实施触及上述登录或执行位置边界，复用最新 dev 已有的 `localQualityReporting.test.ts`、`qualityReporting.test.ts`、`acpConnectionResponseOrder.test.ts` 等相关回归，不重复建设质量模块。目录功能本身不以完整 QMS 集成验收为前提。

## 8. 本方案采用的产品默认值

保留“库 / 专属 / 我的”三个一级入口；“我的”改用来源筛选。点击“使用”自动完成首次下载；另外保留“下载”动作。继承已有本机下载，不自动清空。新版本提示更新，不静默覆盖；云端专用资源允许下载但不承诺本地可运行。上述默认值均可在评审时调整。
