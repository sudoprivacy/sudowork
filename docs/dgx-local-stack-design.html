sudo stack on DGX Spark

在一台本地 NVIDIA DGX Spark（GB10）上跑完整 sudo 技术栈——按请求选本地 GPU 或 云 API，并支持本地 post-training。一层薄路由把两者聚合成一个端点。

架构设计local-first inferenceedge delivery

1. 目标

把 sudo 的整条栈（sudocode / nexus / nova-gateway / gpustack）落到一台桌面级 AI 超算 DGX Spark 上，达成三件事：

  • 本地 GPU vs 云 API 可选——同一个客户端，既能用本地 GB10 上的开源模型，也能用云端各家商用 API。
  • 本地 post-training——在 128GB 统一内存上做 LoRA / QLoRA 级别的微调与持续适配（"meta-learning" 循环）。
  • 可交付的边缘形态——把这套架构做成能交付到"客户自己的一台 GPU 盒子"上的标准部署。

2. 架构：一层薄路由聚合本地与云

长期正确的形态是：客户端只面对一个端点——本地 sudorouter（nova-gateway）。它挂两类 channel：本地 gpustack，以及把远程 sudorouter（sudorouter.ai · SaaS）「stack」上去的一条上游 channel。

为什么要一层本地路由，而不是让客户端各连各的？

能力本地路由带来什么
单一端点客户端只配一个 base_url，本地/云的选择靠模型名路由，客户端无感。
凭证收敛边缘机器上只放一个凭证（SaaS router 的 key），而不是把每家云的 key 都堆上去——尤其适合"不完全可信/借用/客户"的机器。
本地优先 + 回退本地 GPU 忙 / 掉线时自动回退到云，反之亦然。
GUI 友好sudowork 这类非技术界面只看到一个"混合模型列表"。
可观测 / 计费本地/云统一日志、配额、限流的收口点。
对只用 sudocode 的最小场景，也可以先不上本地路由——sudocode 原生支持 per-model 端点（本地模型指 gpustack、云模型指 SaaS）。本地 nova-gateway 是当引入 sudowork GUI、多客户端、统一策略时的长期正确形态。

本地模型如何进入统一列表？——SSOT + 引用式聚合

gpustack 是本地模型的 SSOT：部署一个本地模型，它会自动出现在 gpustack 的 /v1-openai/models（自动建 model-route）。本地 nova-gateway 应当引用这个来源，而不是各存一份会漂移的副本：

  • 调用：本地 channel 按模型名透传给 gpustack——无需为每个本地模型单独配置。
  • 发现（统一 /v1/models 列表，供 GUI 下拉等）：优先请求时实时合并 gpustack 的 /v1/models（保持 SSOT、零漂移）；若网关不支持实时合并，才退到低频小同步把列表并入本地 channel（接受小延迟）。
「小同步」是兜底，不是首选：能实时引用就别缓存副本——否则本地新模型不出现、已删模型残留，都是漂移。设计原则：本地模型的真相只有一个（gpustack），路由层引用它、不复制它。

4. 本地推理选型：统一内存的反直觉

DGX Spark 的特点是大容量、中带宽：128GB 统一内存能装下很大的模型，但内存带宽相对显卡低一个量级。逐 token 生成是带宽瓶颈，所以：

  • 大 dense 模型（如 70B）能装下但吐字慢。
  • 最优解 = 大 MoE 模型（激活参数少）+ 4-bit 量化：容量装下全部专家，每 token 只读一小部分激活参数 → 又快又聪明。Blackwell 原生支持 FP4。
档位代表单机适配
甜点~120B MoE（少激活参数）4-bit✅ 装得下且留足上下文，吐字快，是这台机器"人无我有"的一档
压容量~235B MoE 4-bit⚠️ 顶满内存、慢、上下文紧；官方跑这级用双机互联
稳妥≤32B dense✅ 轻松，但 dense 生成偏慢
⚠️ 统一内存的坑：gpu-memory-utilization 只是 KV-cache 的大小提示，不是安全阀——模型加载 / MoE 预处理的瞬时分配会绕过它，抓走近乎全部内存把操作系统饿死（甚至整机 livelock、只能断电）。统一内存下 GPU 分配与系统内存是同一块物理内存，真正的护栏见 §7：为 OS/SSH 留硬内存保留 + 内存看门狗 + 按峰值选型。

5. 本地 vs 云：把 SaaS 路由 "stack" 成一条上游

本地 sudorouter（nova-gateway）支持自定义 OpenAI 兼容 channel，所以把远程 sudorouter（sudorouter.ai）当作一条上游 channel 加进来即可——一条通道带出所有云模型，本地无需重配每家 key。

6. 本地 post-training 循环

gpustack 只做 serving；post-training 用独立训练栈。两者通过 checkpoint / LoRA 衔接，形成一个本地闭环：

(NGC PyTorch + LoRA/QLoRA)"] T --> CK["checkpoint / adapter"] CK --> SV["gpustack 加载并 serving"] SV --> RT["nova-gateway 路由给客户端"] RT --> D

单 GB10 规模：LoRA / QLoRA + 中小模型现实可行；不适合全量预训练。128GB 统一内存让可微调的模型比普通显卡大得多。

7. 部署要点（通用）

  • 平台：aarch64（ARM）+ Blackwell GPU + 最新 CUDA；整栈按标准 aarch64 Linux port 处理，非重写。
  • 容器化推理：gpustack 经容器运行时把 GPU 透传给引擎容器（vLLM/SGLang）；引擎镜像需与本机 CUDA/架构匹配的变体。
  • 受限网络：在网络受限地区，工具链与镜像走区域镜像源，或"在有出口的机器上取好、经局域网推送"。凭证与站点信息不入库、不入交付文档。
  • 凭证边界：边缘机器上只保留一个上游凭证（SaaS router key）；其余云 key 留在云端路由。
  • 服务地址与物理网卡解耦：边缘机器的网卡一定会变（拔网线、切 WiFi、DHCP 漂移）。路由层的多网卡 failover 是标准能力，但救不了你——真正的坑是组件把自己注册在某张网卡的 IP 上：网卡一消失，该地址随之消失，整个栈停摆，而网络其实一直是通的。推理节点与引擎应宣告与物理网卡无关的地址（容器运行时的宿主机桥接地址，或一张常驻虚拟网卡）。
  • 健壮性（统一内存机型必做）：① 给 OS/SSH 设 cgroup 硬内存保留（MemoryMin）——失控时机器仍可远程恢复、无需断电；② 常驻一个内存看门狗：监控系统可用内存，濒临耗尽才回收失控引擎（读系统级 available，能覆盖绕过 cgroup 记账的 GPU 分配）；③ 引擎容器加 cgroup 内存上限做纵深防御。看门狗设计上宽容、不过早失败——真正的护栏是让失败变廉价（干净 kill）而非频繁触发。一次只常驻一个模型，其余留盘；按峰值（含预处理）而非稳态选型。（本地↔云 fallback 见 §2 / §5。）
